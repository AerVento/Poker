# Poker 成就制作

将设计案落实为可持久化的成就、玩家文案、合适的图标及维护说明。延续本项目的协作方式：理解设计意图，只询问会改变结果的问题；得到必要答案后直接完成授权范围内的工作。

本文代码路径以仓库根目录为基准。先读根目录及目标目录的 `AGENTS.md`，检查工作区已有改动。实现时使用以下项目资料，不复制整个系统重建一套：

- [成就](../../../Docs/Systems/Achievements.md)：定义、事件来源、保存与领奖、客户端缓存和判定口径。
  - 涉及事件接入时重点读其中的“事件来源”一节：来源、事务、版本和订阅方式。
- [UI 规范](../../../Docs/Standards/UIConvention.md)：涉及名称、描述、图标或界面时完整阅读。
- [图标规范](references/icon-style.md)：选择或制作图标时阅读，并查看实际成品参考。
- [对话形成的约定与案例](references/conversation-decisions.md)：遇到相似牌局条件、契约与刑期，或需要回顾用户偏好时阅读。案例只解释各自成就，不替代当前设计。

## 把设计转成可判定的条件

内部为每项整理永久 ID、名称、类别、玩家描述、奖励、目标值、触发事件、判定对象、完成时点、是否需要累计状态。不要要求用户按模板重新提交已经提供的内容。

只澄清设计与已有约定无法决定的关键问题，例如：

- 缺少奖励金额；“赚取”指净盈利还是收到的奖池奖金。
- “达到”指当前数量、历史峰值还是累计获得量；之后减少是否撤销。
- 是否要求摊牌、未弃牌或获胜；立即完成还是等结算；使用哪个时点的公共牌。
- “大两级”指牌型类别还是点数；“差一张”是否包含卡顺、A2345 或已经组成的其他完整牌型。
- “胜利”指任意奖池还是双方共同参与的池子；边池、平分与短码全下是否计入。

一次集中提出相关问题，用简短实例和建议口径帮助确认，不机械穷举所有边界。不要重复询问已明确内容，不为 ID、文件名或普通代码组织请求批准。用户要求“有问题就停下来问”时，停下依赖答案的实现；没有关键疑问则说明理解后开工。

用户随后确认或修正规则时更新同一任务，不把补充消息当成独立需求。对于“还有其他疑问吗”，若已具备实施条件，直接继续实现。

## 选择事件与实现位置

先查看当前代码，通常只需新增 `Assets/Scripts/Game/Achievements` 下的定义：

- 阶段或结算判定继承 `HandAchievement`，覆写 `Evaluate(AchievementContext, accountId, progress)`。
- 即时行动、购买、使用、库存及装备变化，继承 `Achievement` 并实现 `IAchievementHandler<TEvent>`；一个成就可以订阅多个具体事件。
- public、非抽象、默认无参构造的定义由 `AchievementCatalog` 自动发现，不要为每个成就手工改注册表。具体参考 `AccountAchievements.cs`、`AdvancedHandAchievements.cs` 和 `BluffAchievements.cs`。

来源与 UI 类别分开：`table`、`shop`、`inventory`、`collection` 描述业务事实，`Category` 决定页签。先复用已有事实，确实缺少信息时才扩展事件。新来源通过 `IPlayerEventSource.Register` 和 `PlayerEventRegistry.CreateDefault` 接入，不在成就服务堆叠来源判断。

业务事件由服务端权威操作产生。数据库业务在原事务内通过 `IPlayerEventWriter` 追加事件，不在客户端、成功响应或非可靠通知里决定成就。失败和重复请求不生成新的成功事实。事件保存发生当时所需的不可变快照，重放时不以最新库存或装备替代过去状态。

定义实例无玩家状态；只更新 `AchievementProgress`，跨事件状态放 `progress.Data`。沿用服务的去重、封顶、完成时间、奖励快照和独立领奖，不自行发钱。保留已发布 ID、进度和领奖记录；新增定义本身不需要升级数据库。确实改变持久化事件时维护版本、旧解码及 IL2CPP 保留规则，不自动重放所有已消费历史。

### 牌局中容易出错的地方

- 先限定阶段及参与资格，再比较牌型或行动。输赢使用实际 `Pots`，未跟注退款不等于赢池。
- 关系型成就关联同一个对手和同一个有效奖池，不能把不同边池的证据拼在一起。
- `StreetBet` 是本轮累计投入，不能把每条行动的累计值相加。行动先后用 `TurnId` 并限定同一轮；盲注信息在初始阶段快照中。
- 如果设计关注筹码耗尽，Bet、Raise 或 Call 也可能构成全下，不只看按钮名；但不能未经确认把盲注耗尽、断线自动操作算进去。
- 用 `AchievementPatternEvaluator.GetBest` 计算五至七张牌的最佳五张牌。牌型类别差与点数大小不同，不为成就修改正常牌型排序。
- 弃牌玩家的 `BestRank` 可能为空；设计允许比较隐藏手牌时，用服务端快照重新计算，不能因此向客户端同步其底牌。

## 名称、描述与面板

设计案帮助精确理解条件，不直接作为玩家说明全文。用短句保留决定玩家行为的关键信息，详细工程口径和边界写入 `Docs/Systems/Achievements.md`。

用户要求优化名称时，结合扑克、契约或地狱主题落实自然的名称，无需增加起名审批。已选定的梗名或名称，除非要求修改，否则保留。

每有新类别，面板必须有对应筛选页签。当前面板能从目录生成页签，应检查实际分类路径，不重复创建硬编码按钮。复用横幅、列表、分页及领奖流程，日常增加定义不重建 UI prefab。

长描述在横幅内尽可能充分显示，同时保持布局美观，超长部分省略号截断。面板折叠行可截断，但须有小型详情开关展开完整描述；服务端始终提供完整文本。不用缩小字号代替合理布局。

## 图标按主题选择，不为省事一律复用

同系列、同含义图标可复用；当现有符号不能很好表达新成就，或独立主题值得新符号时，主动制作新图。未指定图标不意味着默认永远使用 Cards 或 Champion。

先读图标规范并查看 `cards.png` 等成品。统一墨绿珐琅、暖金圆框、浮雕及象牙白点缀，只改变主题，不混入旧式紫底扁平风格。按游戏中约 92 像素的尺寸考虑辨识度。

需要生成位图时使用当前可用的 imagegen 技能和内置工具，提供已查看的成品作为风格参考，不以程序画占位图替代美术。工具不可用时如实说明，再与用户确定替代路径。

检查生成图的主题、构图、系列一致性和真实 alpha。棋盘格可能被画进 RGB 图片，不能凭预览断言透明。出现问题先尝试有针对性的背景修正；仍失败时按图标规范用完整风格提示重新生成，再检查成品。不无条件重试，也不交付明知不合格的图。

最终图保存到 `Assets/Resources/UI/Achievements` 并接入 `IconPath`，配套 `.meta` 及规范要求的 Sprite 导入设置，不能只留在工具输出目录。完整提示词、参考图和来源追加到 `ArtSources/Achievements/icon-generation.json`。可复用的新主题在图标规范中补充用途。

## 收尾与验证

遵循当前用户明确指定的验证范围。此前协作中用户要求不跑游戏测试，只检查编译、代码和资源；当前任务仍沿用该约定时，不启动 Test Runner、联机/UI 操作测试或构建。不要把过去一次“不跑测试”扩展成禁止所有后续任务验证的永久规则；没有当前约定时按根目录要求执行。人工合成牌局执行判定也属于功能测试，不能换个名称绕过限制。

在允许范围内等待匹配版本 Unity 编译完成，检查新增定义是否被发现、ID/类别/奖励是否正确、图标与 `.meta` 是否完整。不打断用户的 Play Mode 或其他工作，无法完成的检查明确标记未验证。编译和资源检查不代表实战判定已经测试通过。

更新 `Docs/Systems/Achievements.md` 的规则记录；事件机制变化时同步更新其中的“事件来源”一节。检查 diff 和 git status，保留原有用户改动，不提交生成工程或构建产物。

用简洁中文交付新增内容、奖励及重要口径、图标和文档位置、实际执行与未执行的验证。避免复述完整开发过程，或再次要求批准已授权的完成工作。
