# Poker 项目 UI 规范

本文件是 Poker 所有 AI 与开发者进行 UI 工作时必须遵守的项目规范，由根目录 [AGENTS.md](../../AGENTS.md) 强制引用。适用于界面设计、布局、文案、图标、按钮、交互、脚本、预制体、美术资源以及生成 UI 的 Editor 工具；运行时动态生成的 UI 同样适用。

开始 UI 工作前必须完整阅读本文件。新增与本次修改的界面必须满足规范，不能以“旧页面也是这样”“实现起来简单”或“后续再美化”为理由交付不合规界面。发现范围外的旧问题可单独记录，不擅自进行全项目重构或覆盖用户已有改动。

本文是现行通用 UI 标准；其他 UI 设计、审查和实施记录提供功能背景，若视觉、文案或交互约定冲突，以本文为准。用户明确提出新的设计要求时，按该要求执行并同步维护本文，避免产生多套规范。

## 0. 不可省略的设计要求

- **资源有归属**：UI prefab 与脚本按同一功能归档；复用已有组件，不在任意目录散放。
- **风格统一**：沿用现有墨绿、香槟金主题、中文字体、圆角框与成套图标；不能为每个页面另起一套风格。
- **操作直观**：通过布局、图标、状态和反馈让玩家理解操作，不靠大段教学文字解释界面。
- **文案简洁**：除必要的名称、内容、状态、规则与操作标签外，只保留少量装饰性文字和简单介绍。删除无信息增量的提示，保留会影响玩家决策的重要信息。
- **实际验收**：既检查布局和资源引用，也实际操作按钮、返回、滚动与弹窗；能编译不代表 UI 合格。

## 1. 目录与命名

- 所有面板及配套列表项、嵌套预制体按功能放在 `Assets/Prefabs/UI/Panels/<功能目录>/`，单文件面板也使用独立目录，例如 `TitlePanel/TitlePanel.prefab`、`MsgBox/MsgBox.prefab`。
- UI 脚本使用对应的 `Assets/Scripts/UI/<功能目录>/`，同一面板的 partial 文件、列表项、专用滚动组件放在一起；目录变化不改变命名空间或类型名。
- 商城与仓库共用 `ShopPanel/`；主菜单设置与游戏内设置共用 `OptionPanel/`；成就页面、成就横幅与列表项共用 `AchievementPanel/`。
- 其他功能目录为 `DailyTaskPanel/`、`LeaderboardPanel/`、`LoginPanel/`、`LobbyPanel/`、`ChipExchangePanel/`、`RoomListPanel/`、`RoomPanel/`、`GamePanel/`。
- 名片通用组件放在脚本 `Namecards/`；牌面显示 `CardFaceView`、当前牌面 `CardFaceAppearance`、金额格式化等被多个功能共用的组件放在脚本 `Shared/`，对应 prefab 在 `Assets/Prefabs/UI/Shared/`。
- Canvas 与 EventSystem 保留在 `Assets/Prefabs/UI/`；礼物特效与礼物菜单放在 `Assets/Prefabs/Gifts/` 和 `Assets/Scripts/UI/Gifts/`。
- 新增跨功能通用控件 prefab 放在 `Assets/Prefabs/UI/Shared/`，对应脚本放在 `Assets/Scripts/UI/Shared/`；仅供单个功能使用的组件留在该功能目录。`Shared/` prefab 目录按需创建，不预建空目录。不要另建 `UI2/`、`NewUI/`、`TempUI/` 等平行体系。
- UI 主题背景、边框和导航图标统一放在 `Assets/Sprites/UITheme/`；其他图标沿用 `Assets/Sprites/UI/` 的既有分类。物品、名片与礼物美术沿用各自资源目录，不混入通用 UI 主题目录。生成源图与设计记录分别归入 `ArtSources/`、`Docs/`，不得散落在 `Assets` 根目录。
- 不把界面实现塞入 `Game/`、`Network/` 或场景临时脚本；通用 UI 管理设施仍归 `Framework/UI/`。新增 UI 编辑器工具应放入所属功能的 `Editor/` 子目录。
- 面板 prefab 根对象、脚本类型和 prefab 文件名保持一致，例如根对象 `RoomPanel` 挂载 `Game.UI.RoomPanel`。
- 可复用列表项使用职责名称，例如 `Player`、`RoomItem`、`RoundResultListItem`；不要把面板脚本挂在列表项根对象上。

## 2. 层级结构

- 面板根对象使用 `RectTransform`，通常同时具有 `Image` 和对应面板脚本。
- 常用直接子节点命名为 `Title`、`Status`、`Buttons`、`Settings`、`PlayerList` 等，名称表达职责而不是视觉坐标。
- 多按钮区域使用名为 `Buttons` 的容器和 `HorizontalLayoutGroup` 或 `VerticalLayoutGroup`。
- 滚动列表沿用 `ScrollRect -> Viewport -> Content/Players` 结构；内容节点使用布局组件和 `ContentSizeFitter`。
- 输入框和按钮沿用 TextMeshPro/uGUI 组合：`TMP_InputField`、`TextMeshProUGUI`、`Button`。
- 已有可复用视觉元素优先作为 nested prefab 使用，例如牌局中的 `Poker.prefab`，不要复制其内部 YAML。

## 3. 面板脚本与生命周期

- 单实例页面继承 `SingletonPanel<T>`，默认以类型名作为 identifier，例如 `TitlePanel`、`RoomPanel`、`GamePanel`。
- 允许同时存在多个实例的系统弹窗继承 `BasePanel` 并显式使用唯一 identifier，例如 `MsgBox`。
- Inspector 引用使用私有字段和 `[SerializeField]`，字段按 Buttons、Labels、Inputs 等职责分组。
- 在 `OnEnable`/`OnDisable` 中成对注册和移除按钮、输入框及网络事件监听；不要依赖 prefab 中持久化的 `Button.onClick` 业务回调。
- 导航通过 `UIManager.PushPanel` / `PopPanel` 管理，失效页面清理使用既有 `ResetPanels` 流程；`ShowPanel` / `HidePanel` 是兼容入口。不要另建导航栈或按登录状态猜测返回目标。系统级阻塞或确认弹窗放在 `UIManager.Layer.System`。
  - `PushPanel` 不隐藏已有面板，只把目标移到所在渲染层的最前；同一实例不会重复记录。`PopPanel()` 关闭最上层，`PopPanel<T>()` 或 `PopPanel(identifier)` 可移除中间某层，其余面板保持相对顺序。
  - 底层面板保持激活，只有最上层独占指针和键盘输入，防止点击穿透；关闭后恢复下层的输入和有效焦点。
  - 牌面预览是例外：全屏图形遮挡指针点击，不接管导航与键盘焦点，不禁用下层控件。牌局快捷键继续按原规则生效，Esc 关闭预览；出现其他交互面板时关闭预览。
  - `PopPanel` 和 `ClearPanels` 不会触发确认、取消等按钮回调，断线清理不会误发请求。直接调用面板的 `Show`、`Hide` 或销毁也会同步到 `UIManager`。
  - 断线或登出时用 `ResetPanels<TitlePanel>()` 重建层级；设置页返回只 Pop 自身，回到实际来源页面。
- 动态列表项由所属面板持有 prefab 引用，在运行时实例化到布局容器中。

## 4. UIManager 注册

- 所有通过 `UIManager.PushPanel` 打开的面板 prefab 都必须注册到 `Assets/Prefabs/Manager/UIManager.prefab` 的 `_panels` 数组。
- 每种面板脚本类型只能注册一个 prefab；重复类型会在运行时产生警告。
- 新增面板时同时确认 `Canvas.prefab` 的 `Bot`、`Mid`、`Top`、`System` 四层仍存在，并选择符合用途的层级。
- 仅修改现有面板的子节点或序列化引用时，不新增 `_panels` 项。

## 5. 编辑与验证流程

1. 修改脚本后等待 Unity 编译完成并检查 Console error。
2. 通过 Unity Editor 打开目标 prefab stage，再新增节点、组件或设置序列化引用。
3. 保存并关闭 prefab stage，确认 prefab 没有未保存状态。
4. 新资源必须同时生成 `.meta`；移动和删除资源通过 Unity Editor 完成以保留 GUID。
5. 修改 `UIManager.prefab`、面板 prefab 或场景后，在 `Game.unity` 中检查 Missing Script、Missing Reference 和 Console error。
6. 对登录、房间、牌局等流程 UI，至少在 Play Mode 覆盖显示、关闭、断线重建和重复打开。

## 6. 断线恢复与确认弹窗

- 断线和返回房间选择复用现有 `MsgBox`，因为它已经支持确认、取消、系统层显示和独立 identifier。
- 不为单一确认流程创建新的面板 prefab，也不修改 `UIManager._panels`。
- 确认与取消按钮文字由 `MsgBox` 运行时属性设置，以便表达“重新登录”和“离开房间”，同时保持现有 prefab 结构不变。

## 7. 账户入口与设置页

- `TitlePanel` 只负责初始入口，仅保留“开始游戏”和“设置”，不提供退出游戏按钮，不承载账户输入或注册逻辑。
- `LoginPanel` 是独立单实例面板，视觉结构复用 `OptionPanel` 的背景、标题、返回按钮和表单布局。登录与注册使用两个页签，注册额外确认密码；注册成功直接进入已登录状态。
- 认证成功后进入独立 `LobbyPanel`。房间列表、排行榜、成就、每日任务、商城、收藏、设置和筹码兑换采用适合触控的大图标加文字入口，保持统一主题和清晰间距。
- 美金与筹码均使用 `$`，通过不同的统一图标区分；商城、任务与成就使用美金，牌局下注与奖池使用筹码，资产排行榜仅显示合计。筹码兑换面板清楚显示兑换方向、金额与两种余额。
- 账户余额复用 `Assets/Prefabs/UI/Shared/BalanceView.prefab`，显示统一货币图标和完整金额；不另加“美金余额”等重复标题。未知金额显示 `—`，使用自动同步或绑定页面的服务端快照。
- 标题页和大厅中的“设置”入口共用 `OptionPanel`；返回时 Pop 当前页，恢复实际来源页面及其有效焦点，不依据是否登录硬编码目的地。设置入口与返回的视觉形式遵循第 9 节图标约定。
- `OptionPanel` 只读显示不可修改的账户用户名，不使用 `TMP_InputField` 模拟文本；已登录时提供撤销当前持久会话的“登出”按钮，从标题页进入时隐藏登出并返回标题页。
- 认证成功前不得打开 `RoomListPanel`；网络连接成功与账户认证成功是两个独立状态。

## 8. 美术风格、圆角与排版

### 8.1 统一视觉基线

沿用项目现有的深色扑克桌风格：墨绿底色、香槟金重点、暖白文字，使用克制的绒面／皮革质感与金色边框。不能混搭默认 Unity 白灰控件、卡通彩色按钮、无关霓虹配色或不同来源的图标套装。名片、牌面与物品可保留各自主题，但外层导航、容器、按钮和文字层级仍必须统一。

| 用途 | 基准色 |
| --- | --- |
| 深色背景 | `#0B1719` |
| 面板底色 | `#162B2B` |
| 次要按钮 | `#223D39` |
| 公共牌桌面 | `#163E32` |
| 正文 | `#EEE9DD` |
| 次要文字 | `#A4B9AD` |
| 主操作、筹码和当前玩家强调 | `#D9BC7A` |

色值以上表为准。同一角色复用同一颜色；悬停、选中、禁用与风险状态沿用项目对应组件，不逐页随意调色。不能仅靠颜色区分状态，还要结合图形、描边或必要的简短状态文字。

优先复用 `Assets/Sprites/UITheme/` 中的 `ambient-backdrop.png`、`felt-surface.png`、`button-satin.png`、`surface.png`、`outline.png` 及对应现有 prefab 配置。先查看实际素材与代表性页面，确认适合用途再引用；不能只凭文件名自行拼装。需要补充资源时，以现有同类组件为参照，保持材质、光照、边框和色彩一致。

单款牌面、名片或礼物的专属美术约定写在 `ArtSources/` 对应目录的设计文档中（如 [宝石宫廷设计](../../ArtSources/CardFaces/JewelCourt/Design.md)），不写入本规范；这些约定只作用于该款内容本身，不改变外层界面的通用样式。

筹码抽奖采用独立的赌场舞台主题：深紫红背景、写实金属与红漆机身、玻璃转轮、暖金灯光，奖励图标以红金筹码、冰蓝宝石、紫红金冠区分。商城的“筹码抽奖”是打开独立页面的入口按钮，抽奖页提供统一返回图标并保留商城原状态。该主题允许彩色重点、跑马灯和中奖彩纸，避免平涂色块拼成玩具式机身；沿用现有中文字体、圆角组件、输入与音量规则。机身、拉杆、转轮底板按独立模块制作，图案与文字由 UI 控制。抽奖主操作集中于机身下方的单抽和 10 连抽按钮，各自显示总费用；按钮分别使用深红、紫红底色，配暖金细边和高光，不采用黄、绿底色。拉杆保留单抽入口，不再用按钮样式的独立价格牌。抽奖先展示本次实际所得的合并汇总，可确认结束或查看详情。详情按抽取顺序单列展示，每行仅对应一次抽奖，礼包内逐项使用通用物品框单行显示，超宽时横向滑动；整体纵向滚动，返回汇总操作固定可见。不同抽次的重复奖励在详情中不合并，未中奖保留紧凑的一行。动画不得遮挡主要操作或通过全屏强闪烁制造反馈。


### 8.2 圆角是默认要求
- 面板、弹窗、卡片容器、输入框与按钮必须使用一致的圆角体系；不得用默认直角 `Image` 方块拼成正式界面。
- 同类控件复用相同圆角 sprite、边框和九宫格参数。大容器与小按钮可采用匹配尺寸的圆角，但不能逐个任意设定。
- 对可拉伸底板使用正确的九宫格；纹理和图标保持比例。子背景、图片与滚动内容必须符合容器裁切，不能从圆角外露出直角。
- 完整背景、分隔线、牌面／物品原画等按自身用途处理，不为满足圆角要求破坏原画。无底板图标允许透明背景；有底板的图标按钮须复用统一圆角底板。

### 8.3 布局与可读性

- 中文主字体为 `Assets/Font/MsyhSdf.asset`，其备用字体 `MsyhDynamicFallback.asset` 使用项目内的 `msyh.ttc` 动态生成缺失字形，并启用多图集。现有文本继续引用主字体；不要逐个替换为备用字体。动态补字范围以源字体实际包含的字符为限，源字体数据必须随客户端构建保留。
- 沿用现有中文字体与 TextMeshPro 配置。以 1920×1080 为参考，页面标题约 44、正文与按钮约 28、次要信息约 24；同类页面保持一致，不为塞下说明而缩小字号。
- 同一页面明确主要操作，相关信息和操作靠近放置。价格靠近购买入口，任务奖励靠近领取入口，删除入口贴合其作用对象；不要把关联操作散放在远处。
- 使用统一对齐、间距、内边距与按钮尺寸；优先复用相邻页面的布局参数。留白用于分组，不用大段文案填空。
- 图标按钮必须拥有完整、易点击的命中区域；沿用现有同类按钮尺寸，不能只有图标笔画能点击，也不能让相邻热区重叠。
- 长名称、金额、满列表和错误状态必须有明确布局。必要时截断并提供查看完整内容的入口；价格、筹码、截止时间等关键信息不能被无提示截断。
- 必须检查 1920×1080、1366×768，并至少检查一个其他受支持的宽高比。保持主操作可见，使用滚动与合理锚点适配，不能仅靠整体缩小到难以阅读。

### 8.4 名片与牌面的物品图标

每款名片和每套牌面都必须配套一张物品图标，用于仓库、奖励弹窗等约 64～128px 的物品格子；默认款、奖励专属和不可购买款也适用。新增外观时同时制作，主题、主色或核心元素变化时同步更新。名片原画和商城牌面小预览不能代替物品图标。

| 类型 | 文件路径 | 统一构图 |
| --- | --- | --- |
| 名片 | `Assets/Sprites/Items/Namecards/namecard-<商品ID>.png` | 略微倾斜的横向圆角名牌卡，较厚装饰边框，卡面使用该主题的简化标志；所有名片沿用同一造型 |
| 牌面 | `Assets/Sprites/Items/CardFaces/cardface-<商品ID>.png` | 三张扇形展开的扑克牌，最前一张显示主题的简化正面（最多一个大花色符号），后两张显示该套牌背；所有牌面沿用同一扇形构图 |

- 文件名即完整物品 ID，默认款分别为 `namecard-default.png`、`cardface-default.png`。保留原美术的主色和核心元素；主题无法从资料判断时先澄清，不凭 ID 猜测。
- 图标采用统一卡通游戏 UI 风格：粗而干净的深色描边、简单赛璐璐阴影、大块易读形状，不追求写实微纹理或密集细饰。风格参照 `Assets/Sprites/Items/Contracts/`、`Gifts/`；同类造型参照 `Items/Namecards/`、`CardFaces/` 的现有图标。
- 交付为 1:1、1024×1024 RGBA PNG。所有元素完整留在画面内并有余量；物体以外 alpha=0，不绘制底色、棋盘格、地面阴影、背景光雾或外部包围框。卡片自身的装饰边框保留。
- 图中不出现可读文字、字母、数字或牌面点数；允许单个花色符号。必须查看 64px 和 128px 预览，检查主题可辨、轮廓清楚、没有裁切或透明背景伪装。
- 导入为 Sprite (2D and UI)／Single，其他导入参数沿用现有同类物品图标；每张图和新增 Assets 目录都有 `.meta`。替换图标保留原 `.meta` 与 GUID。
- 实际提示词、参考图路径、日期、工具和输出文件写入 `ArtSources/Items/cosmetic-icon-generation.json`，记录结构和提示词写法参照 `contract-icon-generation.json`，保留已有条目。需要保留的原始生成图放在 `ArtSources/Items/`，不进 Assets。
- 配置、图标集资源、Addressables 与发布沿用相关 Skill，并服从当前任务范围；纯美术交付不自动修改这些资源。完整接入后在仓库和奖励弹窗中检查实际物品格子，未接入时如实标记该项未验证。

## 9. 图标按钮与操作语义

已有通用图标语义的操作必须使用统一图标按钮，不得为省事换成矩形文字按钮。图标必须是项目 sprite 或同套风格资源，不能用 TMP 中的 `x`、`<`、Unicode 箭头或 emoji 临时代替正式图标；下面的 ×、箭头仅描述图形语义。

| 操作 | 必须采用的形式与行为 |
| --- | --- |
| 返回 | 统一返回箭头，使用 `Assets/Prefabs/UI/Shared/BackButton.prefab`；位于统一导航位置，回到实际来源页面。 |
| 关闭弹窗 | 弹窗右上角 × 图标，使用 `Assets/Prefabs/UI/Shared/CloseButton.prefab`；只关闭当前弹窗，不隐式执行确认、购买或离开房间。 |
| 删除／移除 | 按项目约定使用作用对象旁的 × 图标，不用“删除”文字按钮替代；通过位置和状态明确作用对象，避免与右上角关闭混淆。 |
| 设置 | 统一齿轮图标，复用 `settings-button.png`。 |
| 静音／恢复声音 | 统一扬声器图标按钮，复用 `audio-on-button.png` 和 `audio-muted-button.png`；各声音通道独立切换，静音显示带斜线的扬声器。 |
| 商城 | 统一购物车图标，复用 `shop-button.png`。 |
| 仓库／收藏 | 统一收纳箱图标，复用 `collection-button.png`。 |
| 上一页／下一页 | 成套左右箭头，配必要的页码和不可用状态；不附加“左右切换页签”等操作教学。 |

物品详情 Tooltip 通过点击外部关闭，不显示右上角关闭按钮。高度随名称和说明文字自适应，短说明不保留大块空白；超出可用高度时滚动查看正文。成就列表中的奖励复用 `RewardItemView`，奖励区固定两格宽度，超出时横向滚动并显示滚动条，不撑高成就行；逐项显示图标与数量，点击查看详情，隐藏成就未解锁时不透露奖励。

牌面预览在全屏半透明黑色遮罩上显示牌面，不显示导航、关闭按钮或操作说明。整张牌可在遮罩上自由拖动，不使用固定预览窗口裁切或限制拖拽位置；点击牌面外的遮罩关闭，双击牌面恢复初始尺寸与位置。

- 返回与关闭按钮作为 nested prefab 复用，根节点的透明 `Image` 提供完整矩形热区，`Icon` 子节点只负责图标显示和状态反馈并关闭 Raycast Target。默认尺寸为 64×64，小型弹窗可按布局使用 58×58 或 46×46；不扩大到相邻控件，也不按图标透明像素裁切热区。业务回调由所属面板注册，共享按钮不自行执行导航。
- 同一动作在不同页面必须保持图形、尺寸体系、边框、配色与交互反馈一致。缺少某个图标时补齐同套组件，不临时混用别的图标包或文字替代品。
- 返回、关闭与删除是不同动作。删除入口不能冒充页面关闭，返回不能默认触发登出或离开房间。永久删除或资产损失等有实际后果的操作，按风险使用简短确认，指出对象和后果；普通关闭、切页不增加确认。
- 图标不能仅为装饰而失去辨识度。确实存在歧义时先改进图形与位置，可提供简短悬停／焦点提示或无障碍名称，不能把所有按钮说明常驻铺满页面，也不能把关键规则只藏在悬停里。
- 业务操作没有清晰通用图标时，允许简短文字按钮，例如“登录”“准备”“跟注 200”“领取”“装备”。主菜单的“开始游戏”等主要入口也可保留短标签。不要为了全图标化让下注、支付和确认的含义更难理解。
- 确认按钮用明确动作，如“购买”“离开房间”，需要时带关键金额；避免所有弹窗都只写“确定”。文案长度服从清晰与必要性，不堆叠介绍。

## 10. 玩家文案：只保留有用信息

### 10.1 可以且应该保留的内容

- 物品名称、必要介绍、用途与效果，任务目标、进度和奖励，房间信息、筹码、价格、数量与牌局状态。
- 会改变玩家决策的重要规则，例如“每日任务 UTC+8 00:00 重置”、有效期、购买限制、消耗、不可撤销后果。规则与时间必须与实际业务一致，不能为了简洁删掉时区或猜测服务器规则。
- 必要的标题、字段标签、短操作名称、简短空状态、错误原因与可执行的恢复操作。
- 少量符合风格的装饰性文字与简单介绍；不能用“装饰”名义包装操作教程或重复页面内容。

### 10.2 必须删除或避免的内容

- 教玩家识别显而易见控件的说明，例如“左右切换页签”“点击返回按钮返回上一页”“点击下方按钮领取奖励”“您可以在这里查看您的物品”。
- 重复标题、按钮或可见状态的说明，长篇欢迎词，以及每块内容都附上一段介绍的布局。
- 工程实现说明，例如“数据通过服务器同步”“点击发送请求”“此界面使用缓存”。用“加载中”“连接已断开”等玩家可理解且确有必要的状态表达。
- 为掩盖图标含义不明、入口难找、步骤过多而添加的提示墙。先修正交互，不把理解成本转嫁给玩家。

| 场景 | 不采用 | 采用 |
| --- | --- | --- |
| 分页 | “点击左右箭头切换不同页面” | 箭头图标与 `1 / 3`，到边界禁用对应箭头。 |
| 返回 | “返回上一页”文字按钮及使用说明 | 统一返回图标。 |
| 物品移除 | “点击此处删除该物品”大按钮 | 物品旁 × 图标；有实际损失时另作简短确认。 |
| 每日重置 | 为减少文字隐藏重置规则 | “每日任务 UTC+8 00:00 重置”（仅在实际规则如此时使用）。 |
| 空仓库 | “这里会显示您拥有的所有物品，请先前往商城购买……” | “暂无物品”，按需要提供统一商城入口。 |
| 余额不足 | 一段服务器拒绝购买的解释 | “筹码不足”，保留价格与余额。 |

每次修改都逐条审核最终可见文案，包括脚本动态赋值、prefab 默认文字、占位符、空状态和错误状态。默认使用短句；物品介绍与重要规则按实际信息量保留，不机械限制字数。低频细节可放在详情中，当前操作必需的价格、风险和时间不能隐藏。

## 11. 以玩家操作为中心的交互

- 进入页面即可辨认内容、当前状态、主要操作和退出方式。常用动作就近完成，不强迫玩家在多个页面间来回跳转或重复确认。
- 返回、关闭的位置和行为稳定；返回列表时尽可能保留页签、筛选与滚动位置。弹窗关闭后恢复原页面的有效焦点，禁止点击穿透。
- 所有交互控件都有正常、悬停／焦点、按下、选中（适用时）、禁用反馈。不可用状态必须看得出，必要时显示简短原因，不能让点击静默失效。
- 异步请求提供简短加载反馈并防止重复提交；失败后给出可恢复操作，不清空不必要的用户输入。不用每次弹框打断正常切页、领取或刷新。
- 成功反馈就近更新余额、进度、已领取／已装备状态，避免同时弹窗、横幅和重复说明。只在确实需要玩家决定时使用确认弹窗。
- 表单提供明确标签、合理焦点顺序和就近错误信息；错误提示不能遮住输入框或主按钮。支持页面已有的键盘导航，不能只在鼠标悬停时才出现必要操作。
- 表单支持 Tab／Shift+Tab；返回与确认仅作用于最上层界面。牌局快捷键在输入框编辑、改键及其他弹窗打开时不得触发。游戏内外设置使用同一份可恢复默认且本地保存的键位配置；返回键固定为 Esc，不提供改键项，其余快捷键可修改，按钮的小字提示随键位更新。
- 游戏内部沿用横屏布局，不添加按屏幕方向重排页面的运行时组件。WebGL 由 WebTemplate 在网页可用区域内按设计宽高比等比显示：空间允许时横屏 FitHeight、竖屏 FitWidth，比例不匹配时留边且不裁切。保持下注等主操作可见且具有足够大的完整热区。加注输入框与执行按钮分离，避免嵌套热区。观战显示开关采用可复用组件；观战名片半透明并显示眼睛图标，弃牌名片持续显示“弃牌”。
- 装饰图像与文本关闭不必要的 Raycast Target；按钮与滚动区域保留完整命中范围，遮罩和布局组件不得阻断正常操作。
- UI 展示服务器权威结果。购买、领取、下注等不能先展示最终成功再忽略服务端失败；断线、超时、页面关闭或轮次变化后，旧回调不得更新已失效界面或再次提交操作。

## 12. AI 执行流程与交付验收

### 开始前

1. 阅读根目录和目标目录的 `AGENTS.md` 以及本规范，检查工作区已有改动。
2. 查看目标页面、至少一个同类页面和将复用的实际美术资源；确认功能目录、现有组件、导航入口与返回路径。历史截图仅作参考，不能替代当前界面的检查。
3. 明确主要操作、必要信息、采用的图标、圆角组件与布局。计划和实现说明写入任务说明或开发文档，不塞进玩家 UI。

### 实现时

1. 按第 1 节放置文件；沿用已有 prefab、样式与序列化引用，动态 UI 复用同样的视觉组件。不要把整页布局硬编码生成作为逃避 prefab 组织和样式复用的捷径。
2. 通过 Unity Editor（可通过 Unity MCP）编辑 prefab 和序列化资源；保持资源 GUID 与 `.meta`，检查 `UIManager` 注册与生命周期。
3. 按第 8～11 节处理视觉、图标、文案与状态，不把默认方块、临时文字按钮和占位说明当成最终设计。

### 完成前必须逐项检查

- [ ] 新增／移动的 UI 脚本、prefab、美术各在规定目录，资源与 `.meta` 配套，未遗留临时资源或重复组件。
- [ ] 实际界面沿用统一主题、字体、圆角、图标和按钮状态；无拉伸、圆角漏底、重叠、遮挡、文字溢出或缺字。
- [ ] 返回、关闭、删除、设置、商城和仓库等采用规定图标；图标语义与实际动作一致。
- [ ] 已逐条检查文案：没有多余操作教学、重复介绍或实现细节；名称、介绍、金额、重要规则和重置时间等必要内容完整。
- [ ] 实际点击验证主操作、返回、关闭、分页／滚动、禁用与重复操作；热区正确、无穿透、无额外无意义确认。
- [ ] 覆盖所涉加载、空数据、长内容、满列表、失败与成功状态；涉及网络时检查断线和失效回调。
- [ ] 在第 8.3 节规定的尺寸与比例查看实际截图，并操作对应界面；不以只读代码、扫描 YAML 或编译通过代替视觉与交互验收。
- [ ] 按根目录 `AGENTS.md` 执行与改动相关的 Unity 编译、场景流程和联机验证；无新增 Missing Script、Missing Reference 或 Console error。
- [ ] 查看最终 diff 和 `git status --short`，仅包含本任务预期修改，未覆盖其他工作；交付说明列出实际检查及未验证项。

视觉修改应保留并查看关键页面／状态的截图证据，本地临时截图放在 `Logs/`；需长期保存的设计基线放入 `Docs/` 对应目录。截图之外还必须实际验证交互。若工具或环境无法运行 Unity、查看界面或执行必要流程，必须明确标记为“未验证”，不得声称 UI 验收通过。

纯规范文档修改无需启动 Unity；检查内容一致性、链接、路径和 diff 即可。修改任何实际 UI 时，必须执行相应验收，不能以本文档已存在作为完成证明。
