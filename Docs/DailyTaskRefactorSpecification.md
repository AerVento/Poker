# 每日任务配置化与组合目标任务书

更新：2026-09-07。状态：已进入实现与验证阶段；实际落点和验证结果见 [实施说明](DailyTaskImplementation.md)。

本文件随讨论更新；已确认规则与建议分开。最新重复次数、type/params 与 Reward 对象设计见 [可重复任务设计](DailyTaskRepeatAndTypeConfiguration.md)，该补充对多轮生命周期优先；本文未注明重复的场景按 maxCompletions=1 理解。现有功能见 [DailyTasks.md](DailyTasks.md)，完整三表配置与示例见 [DailyTaskPoolAndServerConfiguration.md](DailyTaskPoolAndServerConfiguration.md)，实施验收场景见 [DailyTaskCombinationTestCases.md](DailyTaskCombinationTestCases.md)。

本轮用户最新决定覆盖旧稿：按任务系统接收计入时的当前任务池判断；过期不新增进度，不绑定开手日/开手实例；翻牌、转牌形成牌型后立即通知任务系统；已计入进度即使整手异常取消也不回退。旧稿关于整手取消撤销贡献、等待结算确认牌型达标、开手锁定任务的设计已撤销。此前独立 SubAgent 审阅不覆盖这些新决定。

## 1. 目标与范围

将写死的每日福利改为服务器可配置任务。新增同类任务只需修改目标数量、牌型、组合、奖励与所属池配置；新增统计语义才增加代码。任务系统和手牌系统职责独立，手牌系统发布事实，任务系统决定是否增长、完成、到期或发奖。

第一版：直接领取、完成手数、获胜手数、指定牌型、同手 AND、多个独立子目标 ALL、固定日刷新、加权随机多日任务、横向 ScrollView。奖励模型扩展为筹码与物品列表，可合并且原子发放；不加入任意表达式、嵌套 OR/NOT、连续胜场、金额累计或 Web 管理平台。Unity 版本、C# 9、原比赛牌型比较与筹码权威不变。

用户已授权按本任务书实现。运行时、服务端配置、数据库、网络协议与面板改动纳入实施范围。

## 2. 任务类型与计数语义

| 模板 | 累计单位 | 何时计入 |
| --- | --- | --- |
| 直接领取 | 无累计目标 | 领取时检查有效实例及动态资格 |
| 完成手牌次数 | 不同的参与手牌 | 成功正常结算的事件到达任务系统 |
| 获胜次数 | 不同的获胜手牌 | 成功结算且获胜的事件到达任务系统 |
| 组成指定牌型 | 曾形成指定牌型的不同手牌 | 牌型通知到达任务系统，无需等整手结束 |

每个子目标针对同一 HandId 最多 +1；不能按街数、五张组合数、赢池数或重复通知次数累计。同一手可以同时推进多个任务/子目标，不全局消耗手牌。显示封顶为目标数，幂等标记与进度一起保存。

“完成手牌次数 + 指定牌型”的已确认含义是“在 N 手不同的牌中曾组成指定牌型”，不额外附加正常结算条件。因此“游玩 10 手 + 两对”表示 10 手牌各自曾出现两对；不是仅有一手两对就完成另一条独立条件。编辑器用明确描述代替含混的加号标题。

### 同手条件与独立子目标

| 配置含义 | 编译方式 |
| --- | --- |
| 正常完成 10 手 | 一个 CountDistinctHands 目标 10，Participated + HandSettled |
| 10 手各自曾有两对 | 一个目标 10，Participated + PatternObserved(TwoPair) |
| 3 手各自曾有葫芦且获胜 | 一个目标 3，Participated + PatternObserved(FullHouse) + Won + HandSettled |
| 同一手曾有葫芦和四条 | 一个目标 1，两种历史牌型 AND，可发生于不同阶段 |
| 正常玩 10 手，另有 1 手曾有两对 | 两个独立目标：正常手数 10、两对手数 1，AllObjectives |

“曾有葫芦且获胜”不要求最终以葫芦获胜。最终获胜牌型若以后需要应另建条件，不能悄悄替换历史含义。配置顺序不表示事实发生顺序，第一版不开放“先 A 后 B”时序条件。

直接领取不伪造计数目标；累计任务可附加领取时条件。目标达标与当前是否允许领取分开显示。

新增 maxCompletions：每轮达成相同目标可获得一轮奖励，整个实例在有效期内最多完成该次数。分别保存当前轮子目标进度、CompletedCount、ClaimedCount。用户要求牌型任务双进度条：本轮 0/1、完成次数 0/3。每日直接领取配置 3 代表每天三次；多日随机配置 3 代表整个有效期共三次。已确认先领奖再开启下一轮，等待期间不累计；随机实例直到全部轮次完成或到期才释放名额。

## 3. 牌型、参与与获胜

### 牌型匹配

使用本人底牌与当时已公开公共牌。枚举任意合法五张组合，各定义可重叠命中；不是只看最佳牌型，也不是所有较低等级自动成立。允许公共牌独立成牌，不要求使用底牌。不使用其他玩家底牌、未来牌、烧牌。

| 牌型 | 任务定义 |
| --- | --- |
| 一对 | 一个点数至少 2 张；口袋对子可按翻牌前特例命中 |
| 两对 | 两个不同点数各至少 2 张 |
| 三条 | 一个点数至少 3 张 |
| 顺子 | 存在五个连续点数，A2345 有效 |
| 同花 | 存在五张同花色 |
| 葫芦 | 两个不同点数分别可选出 3 张和 2 张 |
| 四条 | 一个点数有 4 张 |
| 同花顺 | 存在同花色五张连续牌 |
| 高牌 | 第一版任务禁用，比赛判定保留 |

三条/四条也满足一对；葫芦同时满足三条、两对、一对；四条加散牌不能满足两对或葫芦，四条加另一对子可以选出葫芦。同花顺同时满足同花和顺子。6 张牌有 6 个五张组合、7 张有 21 个，重复命中只记录一次。皇家同花顺沿用 A 高同花顺，不改原牌型枚举。

### 通知时机与观察边界

- 最新用户示例：翻牌三张完整公开后立即报告该玩家本阶段可组成牌型；转牌公开后同理，不等待本街下注结束或最终结算。翻牌不按三张逐张暂态报告。
- 翻牌前口袋对子沿用此前明确的“翻牌前阶段结束通知”特例；其后各街重复一对不重复加数。
- Fold 前观察过的历史保留，Fold 后公共牌不再新增该玩家观察。断线不等于 Fold，按实际自动操作处理；all-in 仍观察，不能用 CanAct 过滤。
- 旁观、坐出、等待下一手、没发到底牌者不算参与。
- all-in 自动发完公共牌也逐街报告；提前结束时保证应有的牌型/结算事件恰好一次。
- 葫芦后四条分别通知，两种任务各可 +1；后来输、Fold、异常取消均不回退已计入进度。

获胜按任何主池/边池胜者身份判定，平分算赢，只有退回未跟注筹码不算。赢一个池但本手净亏损仍算赢；赢多个池只计一手。Won 只能来自成功正常结算的权威结果。

## 4. 三表配置与编辑器

服务器三份外部 JSON 为权威来源，拟定目录 Config/DailyTasks/：
- TaskDefinitions.json：稳定 ID、名称描述、type、params、maxCompletions；参数编译为目标/条件和每轮 Reward。
- FixedTasks.json：每日固定任务 ID、启用状态、顺序。
- RandomTasks.json：随机容量、候选 ID、权重、有效业务天数。

同 ID 不允许同时进入固定和随机表；server 启动报错并失败，错误定位文件、任务 ID 和字段。随机可以配置 DirectClaim。固定不占随机名额。完整可解析 schemaVersion=2 JSON 与 type/params 模板见配置说明和重复任务设计，示例尚不是现有服务器可加载格式。

任务编译器由条件派生事件时机：有 HandSettled/Won 时仅结算事件计数；只有历史牌型时仅牌型通知计数。配置不需选择代码事件名。移除获胜条件后恢复牌型通知时机，不留下隐藏的结算要求；纯牌型任务不能因收到结算历史再次新增进度。

编辑器三个页签共用加载校验器；总表选择器引用 ID，复制任务/目标生成新 ID，重排序不变 ID；支持保存/重载、撤销重做、清除隐藏字段和实时语义预览。SO 若使用仅为视图或导入，不另存一套权威值。

启动与导出校验包括：类型注册、params 数量/类型/范围、maxCompletions 正整数、空/重复 ID、未知引用、两池交集、版本不一致、未知规则、高牌、非法数量或奖励、数值溢出、非有限权重、不支持的逻辑组合、空累计目标、DirectClaim 错带累计目标等。不得用直接领取兜底非法配置。固定不接受 weight/validityDays，随机 DirectClaim 沿用当日领取规则，validityDays=1。

新配置作用于新实例；现有实例保留目标、每轮奖励、最大完成次数与有效期快照。旧定义下架不能破坏未领历史奖励。迁移每日奖励/东山再起保留原 ID 1/2 与 DailyTask 账本映射，不因迁移重复发奖。

## 5. 刷新、有效期与当前任务池

业务日 UTC+8 每日 00:00，不依赖服务器操作系统时区。

固定：每日刷新所有已有账户，旧实例未完成轮次到期，新日创建新实例重置轮数配额；累计任务已完成未领的各轮奖励保留，直接领取剩余次数不补领。新账号初始化当天固定项。停机恢复仅补当前日，不补造历史福利。

随机：每天第一次有效登录按空位补满；持续在线跨零点视为首次上线，完全离线日不抽。保留仍有效且有剩余可做轮次的任务，不清进度、重置次数或延长有效期。到期任务立即不占位，即使对应手牌未结束。多轮随机实例全部轮次完成或到期才释放名额；单轮原规则是其特例，DirectClaim 在最后一次成功领取时完成全部次数。当日已检查后不因完成、领取、重连或面板操作再次补位。

抽取建议：相对权重、不放回；同池占位的同定义至多一份，只有轮次全部完成或到期、仅剩领奖的历史卡不阻止日后重抽；中间轮待领奖仍占位并排除同定义。候选不足留空，不无限重抽。容量只限制占位随机任务，没有独立每日新增额度。缩容不强删有效任务，扩容等下一次日检查。三天示例：9 月 7 日 20:00 获得，9 月 10 日 00:00 到期。

固定和随机分别持久化 FixedRefreshPeriod / RandomFillPeriod，各自原子幂等，固定刷新不能触发离线随机。账号刷新与事件消费串行，保证先完成当日应有刷新再处理新日事件；事件消费可以兜底应有的在线跨日检查，不重开当天已执行的随机抽签。

### 事件计入规则

任务系统首次处理事件时捕获服务器 CountedAt，只匹配当前有效且正在累计的实例：AssignedAt <= CountedAt < ExpiresAt。WaitingForClaim 期间忽略新增进度并保存事件消费结果，不能领奖后回放补记。恰好到期不算，数据库尚未清理也不算。开手日不锁定任务，新获得实例可参与后续事件并使用该事件携带的整手历史；不追溯重新投递已消费旧事件。

事件消费去重和按手去重分开：
1. EventId 的消费结果保存，包括“没有匹配任务”的结果；重试不重新查询新池而改变原结果。
2. (AccountId, TaskInstanceId, ObjectiveId, HandId) 限制该目标该手至多贡献一次，不加 Street 来绕过去重。

独立实例即使同定义也各有目标与奖励快照，不能以 DefinitionId 或日期替代 TaskInstanceId。

## 6. 完成、领取与取消

最新用户明确：已计入进度不因整手取消回退。普通牌型通知有效处理后增加持久进度，一轮内全部目标达标就记一轮已完成、保存该轮奖励资格并进入 WaitingForClaim，不需等待手牌 Settled。多轮实例不能再用单个 CompletedAt/Claimed 表示；新增完成和已领计数及轮次记录，成功领取且尚未到期、有剩余次数时才开启下一轮；全部轮次完成或到期释放随机名额。无取消回退或追回奖励模型。

例：23:59 葫芦通知使任务 1/1，任务当时有效，则已经完成；00:00 不删除奖励，00:01 正常结算或取消都不撤销。尚未达标的过期任务不再接收后续贡献。含获胜/正常完成条件的目标只有成功结算事件才可能增加，取消不生成这些成功事实。

基础领取约束仍保留：认证连接的本人、房间外、无未结算手牌；每个完成轮次只领一次，整个实例最多 maxCompletions 次。累计目标已完成但仍在房间内，显示完成及当前领取限制，离房后可领；这不是等待确认进度。DirectClaim 当前有效期内领取，旧日不能补领。东山再起领取当刻余额 <=1000，暂曾低余额不永久锁资格。

领取事务重查账号、实例、指定 CompletionOrdinal、完成/有效状态、剩余次数、动态余额和活动手牌，再原子写该轮领取记录、筹码、物品与账本。领取唯一键包含实例与轮次；重试不能自动变成领取下一轮。该轮领取提交与下一轮初始化在同一任务事务内；到期后可领旧已赚奖励，但不能初始化新一轮。重试返回已提交结果，不重复到账。客户端不能指定奖励或伪造时间。

整手取消仍按现有游戏规则退筹码和终结手牌，但任务系统不撤销历史计入；游戏系统与任务系统各自维护状态。已正常结算与取消互斥，误重放取消不能推翻结算或重复发钱；异常恢复保留已提交任务进度，未提交事务回滚不等于回退此前已计入进度。

## 7. OOP 与事件数据流

| 组件 | 职责 |
| --- | --- |
| TaskDefinition / GameTask / ObjectiveDefinition | type+params 编译成强类型规则和 Reward；配置与玩家当前轮/完成/领奖状态分开 |
| ServerTaskConfigurationLoader / TaskDefinitionCompiler | 三表校验、编译组合规则和事件时机 |
| IFormablePatternEvaluator | 可重叠牌型集合，与比赛最佳牌型比较分开 |
| HandFactPublisher / HandFactCollector | 产生参与、阶段牌型和成功结算事实，不读取任务表 |
| IHandCondition / AllHandConditions | 对事实做纯函数匹配，区分待定/满足/不满足 |
| CountDistinctHandsObjective | 提出按手唯一贡献，数量是数据参数 |
| TaskEventHandler / DailyTaskProgressService | 接收事件、匹配当前池、计入时间、幂等和进度完成 |
| FixedTaskRefreshService / RandomTaskAssignmentService | 两套刷新与幂等记录 |
| IWeightedTaskSelector | 仅处理候选及相对权重，可注入随机源 |
| TaskInstanceRepository / TaskProgressRepository | 原子持久化实例、消费结果、贡献去重与完成状态 |
| DailyTaskClaimService / IClaimCondition | 每轮资格重查、次数与筹码/物品奖励的原子事务；GameTask.GetReward 仅生成奖励 |
| DailyTaskPanel / DailyTaskCard | 本人快照、动态卡片、领取请求 |

发布契约：
- PatternObserved：EventId、AccountId、HandId、阶段/序号、本阶段命中集合、截至该时点的历史集合、参与及 Fold 边界。
- HandSettled：EventId、AccountId、HandId、序号、参与、WonAnyPot、整手曾形成牌型集合。
- 取消不是负进度事件；可发送 HandEnded(Cancelled) 供释放事实缓存、防止非法后续事件，不发成功结算事件。

游戏事实不含任务实例、任务配置版本或奖励。收集每个牌面每个有效玩家一次，供所有任务复用；不按每项任务重复枚举。事实留在服务端，客户端只得本人任务状态，不泄漏别人的底牌/牌型历史。

建议使用可靠的本地事实事件通道和独立消费者，每账号按序尽快投递。牌桌在自己的事务中保存事实/待发布事件（outbox），任务在自己的事务中保存消费标记（inbox）、进度与完成状态。两个系统不共享业务事务，不共同回滚；牌桌领域代码只依赖事实发布接口，不查询任务，也不等待任务完成才能结束一手。

事件通道须可靠保存、保序消费、去重，并遵守实际接收计入时间。已提交计入重放只读原结果，尚未成功消费的事件重试仍受实际计入时有效期约束；延迟过期不按事实发生时间补记。任务事务失败不撤销牌桌事实，重试该事件；基础存储不可用时可沿用服务器停服流程，已提交任务进度不回退。

建议目录：Game/Tasks 为纯定义、条件、聚合；Network/Tasks 为配置加载、事实发布适配和服务端消费者；Accounts 为事务存储；Editor 为三表编辑；UI 为卡片与协议。保持原命名空间和无自有 asmdef 结构，新增 Assets 文件配 .meta。

## 8. 横向任务面板与协议

uGUI ScrollView 卡片横向排列，关闭纵向滚动；鼠标/触控可浏览，桌面方向按钮可选。Viewport、Content、布局与裁剪在 prefab 验证，不按日期分页。

卡片以 (AccountId, TaskInstanceId) 绑定；有效固定/随机任务与累计已完成轮次待领取卡共存。到期移除未完成机会但保留已赚未领奖；仍有可做轮次或待领轮次的卡不能因一次领取被删除。显示本轮进度、完成次数条和待领取数；全部完成时本轮保留满条。不能将卡片数当随机占位数。长列表分页/复用需保持滑动锚点，不能午夜自动跳首项或拖拽误领取。

服务器快照包含 TaskStateRevision、实例来源/目标/进度/完成/领取限制等。接受较新版本，拒绝旧响应覆盖状态；分页采用同一修订版本，不把一页缺项误判为删除。关闭面板、换账号、连接替换不能被旧响应重新打开或混入他人状态。

修改网络字段时同步 server state、client projection、Mirror 消息、Serialization.cs 和 UI；原 GrantedAmount 改用实际领取结果，不按具体任务 ID 选常量。所有奖励及完成状态服务端权威；奖励响应扩展物品列表、轮次和多轮计数，旧请求仅实例 ID 的幂等方式需要迁移。

## 9. 实施与验收

## 10. 需求决定与修订记录

上一轮到期/牌桌耦合问题已按用户再次明确的统一规则收敛：只看收到通知时的当前任务池，已计入不回退。23:59 曾有葫芦、00:00 新获得“葫芦且获胜”、00:01 收到成功获胜通知，可用通知内整手葫芦历史推进新任务；不另加“历史必须发生于任务获得后”限制。到期前牌型已达标则完成保留，后续取消不影响。

本轮已确认：第一轮未领奖不累计，领取才开下一轮；随机实例全部轮次完成或到期释放名额。Reward 物品 ID 建议沿用仓库现有 string，避免引入另一套整数映射。

关键修订：
- 任务配置由总表、固定池、随机池分开；固定不占随机容量，随机按业务日有效和首次上线补位。
