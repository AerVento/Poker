# 每日任务组合与编辑器测试用例

更新：2026-09-07。状态：验收设计。新增自动化测试位于 ConfiguredTaskTest.cs，执行结果见 [实施说明](DailyTaskImplementation.md)；本文场景清单不等于全部已执行。

依据：[每日任务重构任务书](DailyTaskRefactorSpecification.md) 与最新 [服务器任务池配置](DailyTaskPoolAndServerConfiguration.md)。重复任务与type/params格式以 [重复任务设计](DailyTaskRepeatAndTypeConfiguration.md) 为最新补充；原C/G/E/R/P用例未注明重复时均采用 maxCompletions=1，类型参数加载改用 schemaVersion=2。原“两对十手”现在由 FormPattern 实现，语义不变。本文件给测试稳定编号，后续实现时映射到实际 NUnit 方法及多人验证场景。产品尚未确认的预期单独标为“待定”，不得把建议写成已通过或已确认。

## 1. 已确认的判断基线

- 翻牌三张完整公开、转牌/河牌公开后立即发布牌型通知；普通牌型目标在任务系统收到通知时增加进度，翻牌前对子保留原特例。
- 本手之后形成别的牌型、Fold、落败或异常取消，都不回退已计入进度；只有未成功提交的事务本身回滚。
- 同一手可分别推进葫芦和四条等不同任务；同一子目标每手最多 +1。
- **组合内包含获胜条件时，中途只记事实，不加该子目标进度；同一手最终胜利且成功结算后才 +1。**
- 任意五张组合满足的牌型均可记录；同一五张组合可以同时满足多个定义，例如同花顺、同花、顺子。
- 不要求使用底牌；Fold 后停止新增观察；口袋对子在翻牌前阶段结束时也可增加一对任务。
- 同点数牌按数量门槛包含：三条/四条计一对，葫芦计三条/两对/一对；第一版不开放高牌任务。
- 赢任意主池或边池、平分均算获胜，只有未跟注退款不算，不要求本手净盈利。
- 按通知计入时的当前池和有效期判断，不绑定开手实例；可使用事件携带的整手历史。任务达标立即完成保留领取、不占随机名额，不等手牌结算；固定独立且不占随机名额。
- 固定表每业务日刷新所有账户，随机表按当日首次上线补空位；持续在线跨零点视为首次上线。固定与随机各自幂等、互不触发，面板只展示。
- 面板为任务卡横向排列的 ScrollView，左右滑动浏览，午夜不清掉待领取历史卡。
- 一个子目标的多个同手条件与多个独立子目标是不同的组合范围。

以下缩写仅用于测试表：P = 本手曾形成指定牌型；W = 本手获胜；S = 本手正常结算。P 在牌型通知检查点提交计数；翻牌前对子在翻牌前阶段结束通知；W/S 只有成功结算后才确定。单独 P 与 P+W 是不同子目标、分别去重。

## 2. 可复用牌面与事件输入

### 牌面 A：葫芦转四条

- 玩家底牌：A♠、A♥。
- 翻牌：A♦、K♣、K♦；最佳牌型为葫芦。
- 转牌：A♣；最佳牌型变为四条。
- 河牌：2♣。

对普通葫芦、普通四条、获胜且曾葫芦三个任务同时评估：翻牌通知收到后只有普通葫芦 +1；转牌通知收到后普通四条 +1；获胜组合只能在最终获胜结算后 +1。合法 Fold 分支必须安排其他玩家仍可行动，不能构造 all-in 后再次主动 Fold 的非法游戏路径。

### 牌面 B：曾有葫芦但落败

- 玩家底牌：K♠、K♥；对手底牌：A♠、A♥。
- 公共牌：K♦、A♣、A♦、2♣、3♦。
- 玩家翻牌即为葫芦，对手为四条；在双方完成合法操作并正常结算的测试中，玩家落败。

预期普通葫芦 +1，获胜且曾葫芦 +0，完成手牌 +1。不能为了制造失败用牌面 A 的 A 四条对一个实际上较小的牌型判负。

### 牌面 C：最佳牌型与任意子集不同

- 玩家底牌：A♠、A♥；翻牌：A♦、K♣、K♦；转牌：Q♣。
- 最佳五张为葫芦；另选 A♠、A♥、A♦、K♣、Q♣ 可得三条。
- 已确认任意组合口径：葫芦和三条目标分别计数。三条也包含一对，完整数量规则见 G21，不按牌型等级自动命中其他目标。

领域层组合测试可使用明确的事实序列，隔离牌型求值错误；同时使用上述真实牌面做端到端测试，不能所有测试都直接伪造 `ObservedPatterns`。

## 3. 组合与计数时机

| 编号 | 输入/步骤 | 预期 |
| --- | --- | --- |
| C01 | 翻牌三张尚未完整公开；完整公开后下注尚未结束 | 不根据逐张发牌暂态计数；三张完整公开即通知，任务消费时 P 可 +1，不等下注结束 |
| C02 | 收到有效 P 通知，相关任务当前未到期 | 普通 P +1；P+W 仍 +0，整手历史供成功结算通知携带 |
| C03 | P 后最终胜利并结算成功 | P 保持原值；P+W +1 |
| C04 | P 后最终落败或合法 Fold | P 保留；P+W +0，不把未获胜视为普通 P 失败 |
| C05 | 本手 W 成立但从未有 P | 纯获胜 +1；P+W +0，不借其他手的牌型补齐 |
| C06 | 本手先 P1 再 P2 | 两个普通任务各 +1；同手 P1 AND P2 在第二个事实可提交时 +1 |
| C07 | 第 A 手仅 P1，第 B 手仅 P2 | 同手 AND 不增长；独立子目标各增长 |
| C08 | 两个子目标：完成 10 手、P 达成 1 手 | 两条分别推进，不要求 10 手全是 P；全部完成后任务才完成 |
| C09 | 同一手多次通知 P；同事件重放；最后结算 | 子目标该手总贡献至多 1；结算事件不对普通牌型子目标重新计数 |
| C10 | 目标为 3，当前 2；本手达成且重复事件到达 | 只变为 3；之后更多手不超过 3，奖励仍只领取一次 |
| C11 | 同一手多个任务、多个子目标同时匹配 | 每个正确的作用域分别去重，不能全局只增加一项 |
| C12 | P+W 与 W+P，两种配置顺序；插入重复 P 条件 | AND 次序不影响结果；重复条件不会产生双倍进度；编辑器提示重复 |
| C13 | 两名玩家同 HandId，一人 P 一人 W | 不把两个账号事实合并，不替任何人满足 P+W |
| C14 | 条件在翻牌未成立、转牌才成立 | 翻牌的“未达成”不永久锁死后续评估 |
| C15 | P+W 的 W 尚未确定 | 状态为待确定，不当成永久失败，也不当成可领取 |
| C16 | 普通 P 已完成，另一个独立 P+W 未完成 | 普通子目标即时封顶；整个任务仍未完成，不把整项任务都延迟或都提前 |
| C17 | 登录即分配每日补给和救济任务，从未开面板，当天未领就跨日 | 两项直接领取实例均过期，不成为永久完成项，不补领；累计目标的已完成实例仍保留 |
| C18 | 当日救济余额 900→5000→900，之后跨日再次变 900 | 当日按领取当刻资格处理；当日曾可领不锁存永久资格，跨日拒绝旧救济，不消耗今天额度 |
| C19 | 登录后从未开面板就游戏；另一账号整日离线；第三账号持续在线跨日 | 固定按日刷新所有账号，随机仅首日在线检查且满池不抽；新日事件查询当前池，不锁定旧手实例 |
| C20 | 登录初始化与重连/连接替换/面板查询/跨日通知重合 | 固定和随机分别幂等；按账号串行确保当日应有刷新完成再消费新日事件，同日不重抽 |

## 4. 牌局路径、牌型与胜利口径

| 编号 | 输入/步骤 | 预期 |
| --- | --- | --- |
| G01 | 翻牌形成 P，所有对手弃牌，本手提前胜利 | P 通知即计数，P+W 待成功结算通知，不要求河牌或摊牌 |
| G02 | 河牌首次形成 P 后正常结束 | 河牌公开即通知普通 P，正常结算通知满足结算依赖目标，两类不漏不重 |
| G03 | 翻牌前 all-in，自动发翻牌、转牌、河牌 | 逐街观察提交；不能跳过中间 P，也不能排除不能行动的玩家 |
| G04 | P 通知已计入，之后本阶段自动 Fold | 保留已计入进度，Fold 后不新增观察 |
| G05 | 断线后自动 Check，仍未 Fold | 继续观察；重连、换连接、座位整理不丢历史，不改账号身份 |
| G06 | 旁观、等待下一手、坐出、未被发底牌 | 均不为该手累计；下一手真实参与后才有资格 |
| G07 | P 前 Fold，后续公共牌使原底牌可以组成 P | 后续不新增该玩家观察；已经发出的 Fold 前合法牌型事实保留 |
| G08 | 牌面 C：最佳葫芦，另一个合法组合可组成三条 | 两个目标都增长，不只计最佳牌型；多个组合命中三条仍只 +1 |
| G09 | 公共牌独立成葫芦，玩家没有 Fold；另一玩家此前 Fold | 未 Fold 玩家可计数，即使组合使用零张底牌；已 Fold 玩家不因新公共牌增长 |
| G10 | 翻牌前口袋 AA，未见翻牌就正常结束 | 翻牌前阶段关闭，一对任务 +1；一对且获胜目标只在本手获胜结算时 +1 |
| G11 | 5/6/7 张、A2345 顺子、A 高同花顺、重复或非法卡牌输入 | 合法牌型求值正确、兼容旧七张结果；非法输入不产生任务进度 |
| G12 | P 后平分主池、只赢边池、赢池但净收益为负 | 都算获胜；P+W 在正常结算后 +1，与净盈利区分 |
| G13 | P 后只有未跟注部分退回，无任何获胜池 | 不算获胜；普通 P 保留，不能只看到账金额为正 |
| G14 | 本手赢多个池、分池奇数筹码分配 | 一手最多 +1；以胜者集合而不是 Award 数值近似判定身份 |
| G15 | 形成 P 后变成更高牌型，最终以其他牌型获胜 | P+W +1；“最终以 P 获胜”若未来开放，应是另一个条件 |
| G16 | 五张为 K♥、Q♥、J♥、10♥、9♥ | 同花顺、同花、顺子目标分别 +1；同手要求三者的 AND 也可完成 |
| G17 | 翻牌前口袋对子，本阶段 Fold 或后来牌面再次形成对子 | 前者在关闭翻牌前阶段时保留达成，后者不为同一子目标重复计数 |
| G18 | 五张明确是四条但无法组成顺子、同花或葫芦 | 不因四条等级较高就增加不存在的顺子、同花、葫芦目标 |
| G19 | 底牌不同花但公共牌同花顺；无玩家 Fold | 零张底牌组合可命中同花顺/同花/顺子；不因本人另有更大或不同牌型丢掉合法组合 |
| G20 | 任务求值遇到纯高牌，或翻牌前两张不同点数；手改配置启用高牌 | 求值集合可为空，不报非法手牌；比赛仍可判高牌；任务配置拒绝高牌，不能默默回退一对或直接领取 |
| G21 | 五张分别为三条加两张不同散牌、四条加散牌、葫芦 | 前者命中三条/一对；四条加散牌命中四条/三条/一对但不命中两对/葫芦；葫芦命中葫芦/三条/两对/一对，各子目标每手仍最多 +1 |

## 5. 编辑器模板与配置生命周期

下列为建议的第一版编辑器契约，实施前随产品确认冻结；测试必须覆盖实际配置编辑、服务器 JSON 读写与序列化；SO 如采用也须验证导入视图，不能仅测试内存工厂。

| 编号 | 操作/配置 | 预期 |
| --- | --- | --- |
| E01 | 直接领取、完成手牌、获胜、指定牌型四个模板分别创建 | 生成明确的条件和计数时机，预览与运行时计划一致 |
| E02 | 给 P 模板加入 W，再移除 W | 加入后计数时机派生为正常结算；移除后恢复牌型通知；不会留下隐藏的结算条件 |
| E03 | P1+P2+W，任意顺序添加 | 整个该子目标都等胜利，不因第一个牌型条件先匹配就计数 |
| E04 | 一个任务包含普通 P、P+W 两个独立子目标 | 各自有评估时机；不能以任务级单一时机误控制全部子目标 |
| E05 | “同手 P+W”与“P 1 手且获胜 1 手” | 预览分别明确“同一手”与“可不同手”；领域测试 C07/C08/C13 佐证作用域 |
| E06 | 将单独完成手牌模板切换为指定牌型模板 | 预览明确由结算计数改为牌型通知计数；完成类的旧隐含条件不会残留 |
| E07 | 同手加入葫芦与四条两个历史条件 | 配置合法；不同阶段先后满足不视为矛盾；若界面提供先后顺序，应拒绝未实现的顺序约束 |
| E08 | 目标为 0/负数/超出类型上限，奖励溢出，空 ID，重复任务或子目标 ID | 导出失败并定位任务、子目标与字段，不能静默回退为直接领取或默认任务 |
| E09 | 无目标列表、无条件列表、未知类型/牌型、空配置项/空编辑器引用、非法 JSON | 只有显式直接领取模板可没有累计目标；其他非法配置报错，不依赖空 AND 自动为真 |
| E10 | W 条件强配阶段时机、高牌任务、未支持的 OR/NOT/嵌套条件 | 编辑器不提供非法选择；手改 JSON 后服务端校验也拒绝，不能只做 Inspector 校验 |
| E11 | 更换牌型、删条件、切换模板、撤销/重做、保存后重新打开配置编辑器 | 隐藏字段不残留；配置、派生时机与预览摘要一致；编辑配置不改变已有玩家状态 |
| E12 | 配置编辑器 → 服务器 JSON → 纯 C# 定义 → 条件计划 | ID、条件参数、目标数、范围和时机一致；对同一事件序列得出相同进度 |
| E13 | 调整列表顺序或仅改名称描述 | 任务和子目标业务身份不变，不清进度；版本策略保持一致 |
| E14 | 复制任务/子目标、改已发布目标数量或牌型、删除后重建 | 复制生成新 ID；已发布规则修改进入新版本；不能用同 ID 偷换规则后重算当天记录 |
| E15 | 任务总量增大、翻页、多个子目标、超长说明、已完成但领取受限 | 动态列表无固定数量假设；状态与进度独立显示；领奖按钮符合服务端结果 |
| E16 | 一对模板及“一对 + 获胜”模板 | 一对可在翻牌前阶段关闭检查；组合获胜仍等待正常结算；不能统一将所有牌型目标限制在翻牌以后 |
| E17 | UI 同时显示今天、昨天及更早同 TaskId，分别领取、刷新、午夜切换 | 卡片/请求按账号+TaskInstanceId 区分，DefinitionId/分配日期不充当唯一身份，进度与领取互不覆盖；累计目标历史用固定奖励且无截止；直接领取旧卡移除并拒绝跨日领取 |
| E18 | 横向 ScrollView 为 0/1/多张卡，1920×1080、1366×768、窄屏 | 横向动态排列、裁剪和空状态正确；鼠标及触控均能访问所有卡，无纵向意外滚动、Missing 引用 |
| E19 | 已滑到中间时跨午夜只读刷新或领取当前卡、当前卡为最后一张 | 累计目标历史待领取卡不清除，直接领取旧卡移除；UI 仅合并服务端已分配任务，首次打开不生成；保持锚点不跳回首项 |
| E20 | 在领取按钮上开始拖拽、快速左右滑动、领取响应超时 | 滑动不触发领取；超时不提前删卡，核对成功后才更新；重复点击仍只到账一次 |
| E21 | 保留大量历史待领取卡，关面板、换端登录、重启服务端、分页加载 | 从服务器恢复全部保留项且可横向访问；不能仅依赖本地列表或只保留固定最近 N 天；旧规则下架后仍能领取固定奖励 |

“顺序无关”只指 AND 条件的配置顺序，不允许打乱真实牌局观察顺序。若以后要“先葫芦再四条”，需增加明确的时序条件，不能假定数组顺序就是规则。

## 6. 事务、重启与业务周期

| 编号 | 故障/时序 | 预期 |
| --- | --- | --- |
| R01 | 任务消费事务在消费标记/进度/完成状态各写入点抛错 | 本次消费原子回滚，可重试；不反向撤销牌桌已提交事实或此前成功消费 |
| R02 | 牌型通知计入成功，随后进程重启，牌桌恢复取消 | 任务已计入进度及完成状态保留；不因牌桌恢复取消而回退 |
| R03 | P 历史已存在，尚未获胜时重连或查询 | P+W 不增长；普通 P 已完成则保持，不等待成功结算确认 |
| R04 | 牌桌结算事务失败；或结算成功、任务消费前崩溃 | 失败不发布成功结算事实；成功的持久事件可以重试投递，按实际计入时间和当前池处理，不重发筹码 |
| R05 | 普通 P 计入后整手异常中止 | 任务进度/完成保留，牌桌自行取消退筹码；取消不发获胜或完成手数的成功事实 |
| R06 | D 日开手跨日，D+1 收到牌型或结算通知 | 按接收时当前有效实例计入，包括开手后新增实例；过期旧实例不新增；实例奖励快照不改 |
| R07 | 一项任务已领取，另一个目标进度增长；并发领取及响应丢失 | 不重开已领取额度；后者正常推进，所有奖励各自最多发一次 |
| R08 | 名称不同/连接相同、账号相同/连接不同、房间编号复用 | 按账号和全局唯一 HandId 区分事实，不串任务或清历史 |

## 9. 测试层次与通过标准

- 纯领域：表驱动组合测试，覆盖条件顺序不变性、不同账号/手牌隔离、单手贡献上限和未达成可继续观察。使用独立预期，不从生产条件计划计算期望值。
- 牌型求值：实际 5/6/7 张牌 fixture，保留原 `Game.Tests.PokerTest` 回归。
- 仓储：真实临时 SQLite、重复投递、并发领取、事务写入点故障、重开连接恢复；不用纯 mock 替代幂等验证。
- Editor：实际编辑与保存服务器 JSON，运行模板切换与重载，若有 SO 导入视图也验证相同语义；不为每个奖励数值写重复测试。
- 集成：至少一个 server 和两个 client。主池/边池、多池及观察者场景按需增至三个以上客户端；覆盖真实阶段推进、提前结束、all-in、断线、领奖与个人信息隔离。
- 开发时固定少量含不同模板、不同子目标的代表配置，不对所有参数笛卡尔积穷举。所有已确认规则用例必须通过；待定规则先定预期再实现，不以任意默认值宣布完成。

本文共 132 个编号用例（C01–C20、G01–G21、E01–E21、R01–R18、P01–P30、M01–M22），均为待实施验收场景，不是新增或通过的自动化测试数量。本轮加入多轮领取、完整任务类、type/params和物品Reward；此前独立审阅不覆盖这些新决定。
