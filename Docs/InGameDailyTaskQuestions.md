# 游戏内每日任务：实际冲突与待确认规则

日期：2026-09-09。状态：已由用户确认，按下述决定实施。

## 改动前的代码事实

1. `SqliteAccountRepository.SettleHand` 原先要求账户余额等于开手余额，结算写入“开手余额 − 投入 + 赢得 + 退还”。弃牌后立即向账户增加奖励，会导致 `InvalidDistribution`，不能只移除“房间外才能领奖”的校验。
2. `GameManager` 的 `Chips` 是手中剩余可用筹码，数据库 `player_accounts.chips` 在一手内仍是开手余额；`HandStartingChips` 限制本手投入。二者在下注后不同。
3. `ConfiguredTaskService` 的任务领取条件目前读数据库余额。低余额补助因此可能出现“手中余额已低于门槛，数据库余额仍高于门槛”的情况。
4. 删除随机任务会自动发放当前可领轮次，因此必须与手动领取遵守同一阶段限制，确认弹窗打开后也必须再次校验。
5. 旁观/等待下一手玩家的 `IsFold` 默认也可能为 true，不能直接把这个布尔值当作“本手已经弃牌”。

## 已确认的决定

- 奖励立即入账户与背包，筹码下一手可用。
- 低余额任务继续按未结算的账户余额判断。

以下保留当时的选项及冲突依据。

### A. 弃牌后奖励何时生效

已选择：领取后立即入账户与背包，筹码在下一手可用；本手的投入、边池与手牌统计保持原样。结算按本手净输赢增减账户，并明确记录/核验本手期间的任务奖励，避免把任何余额差异当作合法奖励。崩溃恢复也应保留已经领取的奖励。

替代：弃牌后可领取，但奖励暂存，直到本手结算完成再入账；这需要待发奖励存储和恢复流程。

### B. 手牌期间低余额领取条件

推荐：已弃牌时按剩余可用筹码（扣除本手投入并计入本手已领取奖励）判断。这样“身上有多少钱”的条件与实际可用余额一致；奖励仍按 A 的确认方案入账。

已选择：继续按尚未结算的账户余额判断；逻辑改动较小，但 UI 当前手中筹码可能已低于门槛，补助仍不可领。

## 不需要改变的规则

- 两手之间结算完成时允许领取；进行中的手牌要求本人确实参与本手且已弃牌。
- 未弃牌、all-in、仅旁观/等待下一手的玩家在手牌进行中只查看。
- 任务删除的自动领奖走同样的权限与原子入账流程。
- 每日任务页不增加操作教学文案，用按钮状态表达当前可操作性。
