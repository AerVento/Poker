# 服务器任务三表配置与刷新规则

更新：2026-09-07。状态：配置规范；实际服务器配置目录为 Config/DailyTasks，schemaVersion=2 的 type/params 格式以重复任务设计和实际三表为准。

本稿是 [每日任务书](DailyTaskRefactorSpecification.md) 的分配与事件处理规范。重复次数及类型参数以 [重复任务设计](DailyTaskRepeatAndTypeConfiguration.md) 为最新补充；未标注重复的例子默认次数为 1。最新决定：任务系统在计入事件时查询当前任务池，已过期实例不新增进度；撤销开手绑定任务实例及跨到期宽限方案。任务内容、固定池、随机池仍分为三表。

## 1. 三张表的职责

| 表 | 保存内容 |
| --- | --- |
| 总任务列表 `TaskDefinitions.json` | 稳定 ID、名称、type、params、maxCompletions（目标、条件和单轮奖励由类型参数表达） |
| 固定任务表 `FixedTasks.json` | 固定任务 ID 引用、启用状态、显示顺序 |
| 随机任务表 `RandomTasks.json` | 随机池容量，以及候选任务 ID、启用状态、权重、有效业务天数 |

同一个任务 ID 不得同时存在于固定和随机表，包括禁用行也建议检查；服务器启动时报告文件、行对应任务 ID 与错误原因，拒绝启动任务服务并让服务器启动失败，不能静默去重或只忽略其中一份。总表无需固定/随机标签。

固定任务每业务日刷新各账户，不占随机名额。随机任务当日首次有效登录补空位；延续此前确认，持续在线跨零点视为新业务日首次上线。面板只展示，不触发重新分配。两个刷新服务、幂等记录分开，固定刷新不替离线账户抽随机任务。

建议部署于 `Config/DailyTasks/`，三表同一 schemaVersion/revision 整套校验和生效。编辑器提供三个对应页签，读写同一服务器 JSON；无需为每个任务写代码，不增加另一套 SO 权威数值。

## 2. type + params 的完整配置示例

新增可完成次数与任务类参数规范见 [可重复任务设计](DailyTaskRepeatAndTypeConfiguration.md)，该文对多轮状态与参数格式优先。以下 schemaVersion=2 替换旧 kind/objectives/reward 格式；现有服务器尚未实现加载。

完整文件：[总任务列表](Examples/DailyTasks/TaskDefinitions.json)、[固定任务表](Examples/DailyTasks/FixedTasks.json)、[随机任务表](Examples/DailyTasks/RandomTasks.json)。

### 2.1 总任务列表

```json
{
  "schemaVersion": 2,
  "revision": "daily-tasks-v5",
  "tasks": [
    {
      "id": "daily_supply",
      "name": "每日奖励",
      "type": "DirectClaim",
      "params": [
        1000
      ],
      "maxCompletions": 3
    },
    {
      "id": "comeback",
      "name": "东山再起",
      "type": "DirectClaimWhenAtMost",
      "params": [
        2000,
        1000
      ],
      "maxCompletions": 1
    },
    {
      "id": "two_pair_10",
      "name": "两对十手",
      "type": "FormPattern",
      "params": [
        1500,
        "TwoPair",
        10
      ],
      "maxCompletions": 1
    },
    {
      "id": "full_house_1_repeat_3",
      "name": "葫芦三次",
      "type": "FormPattern",
      "params": [
        500,
        "FullHouse",
        1
      ],
      "maxCompletions": 3
    }
  ]
}
```

maxCompletions 是该实例有效期内可完成的轮数，每轮奖励放在 params[0]。数字是筹码奖励简写，完整 Reward 对象可包含 chip 和 items。每日奖励每天 3 次，每次 1000；东山再起示例仍为 1 次，保持当前余额 <=1000 的既有边界，因此使用 DirectClaimWhenAtMost。

DirectClaimWhenLesserThan 明确定义严格小于，不能默默当成小于等于。FormPattern 的参数为 [每轮奖励, 指定牌型, 每轮所需不同手数]：two_pair_10 需要 10 手各有两对、共一轮；full_house_1_repeat_3 每轮 1 手葫芦、整个期限共 3 轮。PlayHands、WinHands、WinWithPattern 等其余具体类及高级 CountHands/AllObjectives 组合见重复任务设计的完整注册表。目标条件决定牌型通知或成功结算的计入时机。

所有实际领取仍由服务端统一检查认证、房间外、无未决手牌等基础资格；任务类 Available 不能绕过这些限制。每个完成轮次只发奖一次，不再是整个实例只发一次。

### 2.2 固定任务表

```json
{
  "schemaVersion": 2,
  "revision": "daily-tasks-v5",
  "entries": [
    {
      "taskId": "daily_supply",
      "enabled": true,
      "sortOrder": 0
    },
    {
      "taskId": "comeback",
      "enabled": true,
      "sortOrder": 1
    }
  ]
}
```

每天新建固定实例，新的 maxCompletions 配额随新实例开始。直接领取剩余次数不能跨日补领；累计目标已赚取的未领轮次保留。固定表不接受随机权重和多日有效期。

### 2.3 随机任务表

```json
{
  "schemaVersion": 2,
  "revision": "daily-tasks-v5",
  "capacity": 2,
  "entries": [
    {
      "taskId": "two_pair_10",
      "enabled": true,
      "weight": 60,
      "validityDays": 3
    },
    {
      "taskId": "full_house_1_repeat_3",
      "enabled": true,
      "weight": 40,
      "validityDays": 3
    }
  ]
}
```

容量 2，有两个候选，两个都可抽时都会获得；权重影响选择顺序，不能把 60/40 误读成最终各只有 60%/40% 获得概率。有更多候选或仅一个空位时，才会影响本次获得哪个。validityDays=3 的重复任务是三天合计最多完成 3 轮，不是每天 3 轮；每日补位不会重置既有实例。

### 2.4 独立子目标与随机直接领取

“玩 10 手并且另有 1 手两对”用 AllObjectives + 两个 CountDistinctHands 子目标；完整 type/params 写法见可重复任务设计第 4.2 节。不同于 10 手各有两对，编辑器必须预览准确含义。

DirectClaim 可以放随机表，maxCompletions 也适用。将 daily_supply 的固定引用移除，再由随机表引用即可，不允许同时在两张池表。沿用此前“不跨日补领”，随机直接领取第一版 validityDays=1。每次领取动态重查资格，不能一次满足低余额就自动发满所有轮次。

## 3. 固定刷新与随机补位

固定流程：

1. UTC+8 零点按固定表为所有已有账户生成当日实例；账号、业务日幂等。
2. 旧日未完成轮次到期；累计目标已完成但未领的各轮奖励保留，每日新实例使用新 ID。
3. 新注册账户初始化当日固定项；停机跨日恢复只确保当前日，不补造过去的可领取福利。
4. 可以分账户事务重试，登录兜底不导致同日重复发放。

随机流程：

1. 当日首次有效登录，或持续在线跨业务日，取得账号级串行处理权限。
2. 使用服务器当前时间排除到期实例；按已确认规则，全部轮次完成的实例不占位，仍有剩余轮次的有效实例继续占位，包括中间轮等待领奖。不能因首轮领奖就删除整个实例。
3. 缺口 = max(0, capacity - 占位随机数)。到期实例即使有未决手牌也不占位。
4. 排除本池仍占位的同定义候选，按权重不放回抽取缺口数量。仅剩待领奖的历史卡不阻止日后重抽；仍有剩余可做轮次的有效实例继续占位，排除同定义候选。
5. 新实例与 RandomFillPeriod 原子提交，满池或候选不足也记录当天已检查。重连、重试、同日再打开面板不重抽。
6. 同日检查后才释放空位，等下个业务日首次上线再补。全离线日不抽取，回来只检查当前日。

权重 0 排除；负数、非有限值报错。候选不足保留空位，不复制占位定义或无限循环。配置扩容不重开已经执行的当日补位；缩容不强删有效实例，超容期间不补，等待完成/到期自然收敛。

## 4. 当前任务池与计入时间

用户已确认：

- 手牌系统只发布事实，不读取任务表、不绑定 TaskInstanceId、不决定某项任务是否增长。
- 任务系统在收到可计数事件时，只评估该账号当前池中有效且处于累计中的任务；等待领取的中间轮虽然占位，也不接收新进度。
- 使用计入时的服务器时间，资格区间 AssignedAt <= CountedAt < ExpiresAt；恰好到期不计。不以客户端时间、开手日期或开手时配置宽限。
- 随机任务按业务日有效：9 月 7 日 20:00 获得 3 天任务，9 月 10 日 00:00 到期。
- 即使清理定时器还未执行，逻辑上过期也不计数，不能仅检查数据库行“还存在”。
- 同一手跨日可在新的有效实例中计入后续事件，事件所带整手历史可以包含任务获得前的事实；不回放旧事件替新实例补进度。已消费事件重试恢复原处理结果，不能改投新任务。
- 到期立即释放随机名额，未完成旧任务不等待手牌；已完成卡独立保留至领取。计数/消费记录用于去重和审计，不用于取消回退。

翻牌三张完整公开后、转牌或河牌公开后立即发送牌型通知，任务收到时计入，不等待下注阶段结束。翻牌前对子沿用翻牌前阶段结束通知的既有特例。纯完成手数、获胜组合在成功结算通知计入。比如任务 00:00 到期，牌型通知 00:01 才到达，旧任务 +0；23:59 已计入则取消也不回退。普通牌型不会在结算通知中重新计数。

账号任务事件与刷新串行处理，每次首次处理事件使用同一事务内捕获的 CountedAt；重放返回原去重结果。事件通道按账号保序、尽快投递；可靠落盘和重试不改变接收计入时间规则，迟到事件不按发生时间宽限。

## 5. 独立系统的事件契约与 OOP

两个系统通过服务端事实事件解耦，独立管理自己的状态与事务。牌桌只发布已发生事实，不引用任务目录、当前任务池或任务服务；任务消费者自行决定是否匹配、有效及完成。事件投递必须可靠和可去重，不能把关键通知仅存在内存中。

| 事件 | 最小事实 | 任务侧用途 |
| --- | --- | --- |
| PatternObserved | EventId、AccountId、HandId、序号/阶段、参与状态、本阶段可组成牌型、Fold 前整手历史 | 普通牌型组合计数 |
| HandSettled | EventId、AccountId、HandId、序号、WonAnyPot、整手曾形成牌型集合 | 完成/获胜目标计数；不再次计算普通牌型目标 |
| HandEnded(Cancelled)，可选终态通知 | EventId、HandId、序号、终态 | 释放事实缓存及终态去重；不减任务进度 |

ObservedPatterns 包含任意合法组合的重叠命中；不能只发“最终以四条胜利”，否则会丢失翻牌葫芦。Fold 后不新增观察，all-in 继续观察。赢任意奖池或平分算赢，未跟注退款不算。只向任务服务发送服务端事实，不对其他客户端公开个人历史。

事件本身不包含任务实例或目录版本，游戏规则不因任务增删而改变。TaskEventHandler 读取当前实例快照，组合条件计算进度。计入结果保存 EventId/CountedAt/实例贡献；事件幂等和子目标 HandId 去重分别保证。无任务匹配的事件也要保存消费结果，避免晚些重放污染新任务。

任务新增进度只看通知到达时当前池中可推进的实例/轮次；一旦计入不再回退。牌型计数无需等手牌正常结算确认，牌桌取消不触发任务撤销。任务系统不需要保存待决贡献或等待手牌结束来判定过期名额。

建议组件：

- ServerTaskConfigurationLoader：三表解析、类型/引用/交集校验，失败阻止 server 启动。
- TaskDefinitionCompiler：目标条件与合法计数检查点；模板数量/牌型改变不增加新类。
- FixedTaskRefreshService、RandomTaskAssignmentService：独立刷新记录 FixedRefreshPeriod / RandomFillPeriod。
- IWeightedTaskSelector：候选及相对权重选择，可注入随机源测试。
- TaskEventHandler / DailyTaskProgressService：当前池匹配、时间判断、去重与进度。
- TaskInstanceLifecycleService：到期、完成、占位及领取保留。
- TaskProgressRepository：消费去重、按手去重、进度和完成状态的原子持久化，不提供手牌取消回退接口。
- DailyTaskClaimService：基础资格、动态条件、实例幂等、奖励与账本原子提交。

建议通过可靠本地事件通道实现：牌桌在自己的事务中写入事实与待发布事件（outbox），任务在自己的事务中提交消费标记（inbox）、进度和完成状态。两者不共享业务事务，也不共同回滚；每账号按序尽快投递。发布成功结算事件必须与真实结算结果一致，事件通道不生成臆测的胜利。进度消费失败只重试任务事务；已成功计入不因后续牌桌取消而撤销。

## 6. 完成轮次、领取与取消

用户最新明确可重复完成：每轮达标就记一次已完成与对应奖励资格，不等待手牌结算；后续取消不回退。整个实例不再用一个 CompletedAt/Claimed 布尔值概括，区分本轮进度、CompletedCount、ClaimedCount、各轮完成记录和次数上限。

23:59 葫芦通知完成一轮，则这一轮已经赚取，00:00 到期不删除该轮待领奖，00:01 手牌结算或取消也不撤销。尚未完成的轮次到期后不能新增；DirectClaim 剩余次数仍只在当日可用，不成为历史永久奖励。

用户已确认一轮完成后必须先领奖再开下一轮，等待领取期间不累计、不补记；随机实例直到全部轮次完成或到期才释放名额。最后一轮达标尚未领取也释放；DirectClaim 的最后一轮在领取成功时完成。

用户明确只看当前池，所以跨日后新获任务可以使用后续成功结算通知中的整手历史。重复轮次内部仍要跨轮去重，不能用同手多次通知完成全部次数；配置变更不覆盖原实例快照。

每次领取由服务端按实例与 CompletionOrdinal 幂等，仍检查房间外、无未决手牌等基础资格。领奖与下一轮初始化原子执行，过期后只发已赚旧轮奖励、不再开新轮。DirectClaimWhenLesserThan/AtMost 每领一轮都重新检查当前筹码；允许三次不表示一次满足资格就锁定三份奖励。

## 7. 发布与验收

服务端启动校验：type 必须已注册，params 数量与每项类型/范围严格符合类型签名，maxCompletions 为可安全处理的正整数；总表/子目标 ID 唯一且非空，池内不重复且两池 ID 交集为空，所有引用存在；三表版本一致；容量非负整数、目标/有效天数正整数、奖励合法且不溢出、权重非负有限；类型/牌型/参数受支持，高牌禁用；直接领取类型不接受目标参数且随机有效期为 1；固定表不得带随机字段。具体参数上限由实现定义并在编辑器共用校验器，错误标明文件和字段路径。

新配置只用于新分配实例，旧目标、单轮奖励、最大轮数、期限和进度快照不被重写。旧实例永久领奖不能依赖目录仍有原定义。界面横向 ScrollView 绑定 TaskInstanceId，卡片数不用于随机名额统计。

测试覆盖：三份完整示例解析/编译；两种“两对十手”语义；领取余额边界与顺序；随机直接领取、当日到期；跨表重复启动失败；到期前后和等于到期时；清理延迟；刷新/事件并发；无匹配事件重放；结算不补普通牌型进度；异常取消不回退；跨日新任务使用整手历史；可靠事件重试与独立事务；权重和容量。

配置示例、任务书和验收清单是设计产物，尚未实现加载器、事件接入或运行新增自动化测试。
