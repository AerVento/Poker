# 名片商店与外观装备实施计划

更新：2026-09-06。状态：已实现 Unity 商店、商品 SO 配置和扩展美术，共 12 款（含免费默认款），每页 4 款、共 3 页。见 [UI 与配置说明](NamecardShopUI.md) 和 [美术记录](NamecardArtNotes.md)。真实购买、数据库库存及房间／牌桌装备同步已接入；不制作筛选功能。新增款式操作见 [操作指南](AddingNamecards.md)。此前结算、排行榜等改造的结果见 [验证记录](HandSettlementValidation.md)。

## 1. 用户已经确认

1. 新增商店，使用现有账户筹码余额购买名片外观，不新增充值币或独立钱包。消费后账户余额减少，排行榜按减少后的余额重新排名。
2. 名片对应用户截图中的玩家卡片，应用到 **GamePanel 本桌玩家列表和 RoomPanel 房间等待页**。其他玩家和旁观者应看见装备者的外观。
3. 商品永久拥有，每款只能购买一次，所有权随账户保存，重登、重连和服务器重启后保留。
4. 商品与仓库共用逻辑：同一商品卡片根据所有权显示“购买”或“装备”。用户已确认不提供筛选功能，采用每页 4 款的分页展示，每款均有名称与介绍；商品目录、商品卡组件和账户库存共用，不制作两套独立购买／装备逻辑。
5. 已购买的商品由玩家点击“装备”使用，不在购买后自动更换外观。同时装备一款；当前款显示“已装备”并禁止重复提交。切换外观不再次收费。
6. 用户已确认：购买名片后余额降到 1,000 或以下，仍可领取当日未领取的东山再起；继续按当前余额、房间外／无活动手牌及每日一次规则判断。
7. 首批制作多款酷炫名片，**使用 Image 生图制作底图／装饰素材**，再接入 Unity。玩家名、金额、倒计时、房主、D/SB/BB、准备与断线状态仍由 UI 动态绘制，不能烘焙进图片。

默认款“经典”也放在第一页第一个位置，新玩家天然拥有并默认装备，无需购买或解锁；任何账户都可免费切回默认外观。名片只改变视觉表现，不提供牌局属性或操作优势。

## 4. 界面与操作

大厅增加“商店”入口，通过 `UIManager` 注册及导航。商店顶部显示当前余额，中部两行两列，每页最多 4 款，不设置分类、搜索或拥有状态筛选。每张商品卡包含预览、名称、介绍、价格或拥有状态；底部显示上一页、页码、下一页、收藏数量和当前商品范围。首尾页禁止越界，最后一页不足 4 款时隐藏空位；购买／装备后的结果就地刷新。

商品状态：

| 账户状态 | 卡片按钮 | 点击行为 |
| --- | --- | --- |
| 尚未购买且余额足够 | 购买 | 打开确认框，展示商品、价格及预计剩余余额；确认后向服务器购买。 |
| 尚未购买且余额不足 | 余额不足 | 不提交；余额刷新后可恢复购买状态。服务端仍独立校验。 |
| 永久拥有但未装备 | 装备 | 请求更换当前款式；成功后旧款回到“装备”。 |
| 当前装备 | 已装备 | 禁止重复提交，不再次收费。 |
| 免费默认款 | 装备／已装备 | 无须购买，无库存记录也可使用。 |
| 请求处理中 | 暂时禁用 | 防止重复点击；超时后允许用原幂等编号重试或重新查询库存。 |

确认购买时以服务端目录为准。若预览后价格／目录版本变化，返回明确结果并刷新确认信息，不按用户未看到的新价格直接扣费。购买成功后更新余额、库存和按钮；不立即装备。装备成功后更新预览及“已装备”状态。

登出、账号切换、断线、关闭面板后，过期回复不得作用到其他账号、重新弹出界面或覆盖新请求。返回大厅及断线回标题页沿用现有导航。排行榜没有手内实时排名保证；购物结束后重新打开／刷新时显示新余额排名。

## 5. 数据、服务端与网络设计

已实现展示层：NamecardProductSO 配置单款商品；NamecardCatalogSO 配置目录；ShopPanel 负责每页 4 款分页并接收账户视图；ShopItemCard 显示图像和文案。UI 只发出购买／装备意图，不修改账户或库存。Editor 专用预览使用局部示例数据，离开预览即丢弃。

以下服务端设计已实施：商品 SO 是配置编辑来源，发布流程从目录导出 ID、价格、默认款规则及版本的纯数据快照。服务端使用发布快照验证价格，不接受客户端修改的 SO 作为扣款依据。UI 已以服务端报价和版本确认；客户端／服务端配置不同须刷新确认信息，不能直接按未确认的新价格收费。默认款始终免费、天然拥有，不写购买库存记录。


- 新增服务端商品目录：稳定 ID、售价、启用状态、目录版本。客户端保留对应 ID 的展示名、美术及预览；请求不接受任意价格、用户指定账户 ID 或资源路径。
- schema 5 新增账户物品表（账户＋商品唯一）、账户 equipped_namecard 字段（空字符串表示经典）、请求结果表（账户＋请求 ID 唯一）；外键与金额范围约束保持一致。
- `PurchaseNamecard` 在一个 SQLite 事务中校验认证账户、商品、目录版本、所有权、活动手牌、可用余额，再更新余额／Version、插入 `ShopPurchase` 负数账本、库存及保存的成功结果。任何失败全部回滚。
- `EquipNamecard` 校验默认款或真实所有权，再更新当前装备；不扣款。不能把客户端“拥有”的布尔值当作证据，装备变更也应防重复和旧请求覆盖。
- 沿用 `GuardedAccountRepository`：余额不足、已拥有、无此商品、房间内禁用、目录过期是正常业务拒绝；数据库异常沿用已确认的致命停服策略。重启后已提交购买同时保留扣款和物品；未提交购买两者都不存在。
- 统一消息 `NamecardShopRequest/Response`，Action 区分读取、购买与装备，包含会话所属账户校验、请求编号和必要状态。服务端验证当前连接绑定身份，拒绝顶号旧连接；限制频率。
- 商店与库存共用 `ShopPanel` 的账户快照和 `ShopItemCard` 展示状态：商品描述＋是否拥有＋是否装备。库存查询不产生购买或换装副作用；装备 ID 通过公开房间／牌局视图同步给所有观察者。
- 结算后账户同步、每日奖励后同步和购买后同步使用同一余额刷新入口，避免全局状态、会话副本、排行榜与商店各自保留过期余额。

## 6. Image 生图与名片显示

参考截图的横向圆角卡片，约 2.7:1。首批及扩展共生成 11 款独立的 2048×768 PNG 美术，比例为 8:3，原图存放在 `Docs/NamecardPreviews/`。原图不包含姓名、金额等 UI 文本。接入时再按当前 prefab 实际比例确定导入分辨率、裁切或遮罩方式；装饰不能被九宫格拉伸变形。保留原始提示词和版本记录，不直接拉伸用户截图。

| 主题建议 | Image 图像方向 | UI 信息留白 |
| --- | --- | --- |
| 星河 | 深蓝紫星云、边缘星光与细金属线，中心深色。 | 左上姓名、左下筹码、右上倒计时区域低对比、无密集星点。 |
| 赤焰 | 黑曜石与暗红金属，火焰沿两侧和底边展开。 | 火焰不能覆盖姓名、金额、盲注徽记；不用整块高亮红底。 |
| 霓虹 | 深色科技底、青蓝／紫红能量线、局部光轨。 | 中间保持干净，不把线条画成可交互按钮。 |
| 鎏金 | 深墨绿／黑金、拉丝金属纹理与克制的金色装饰。 | 避免与“当前行动者”金边混淆，独立保留业务状态标记。 |

生成素材不包含文字、金额、玩家名、卡牌花色状态徽记或水印。流光属于 Unity 动画层，Image 负责静态底图；不能宣称生成一张 PNG 就实现了动态效果。视觉层级依次为名片底图、装饰光、状态边框／遮罩、玩家文字与状态图标；动态卡片保持完整数字金额的可读性。

资源已导入 `Assets/Sprites/Namecards/`，由 Unity 管理 `.meta`；GamePanel 与 RoomPanel 实际玩家行通过 NamecardAppearance 接入。时轮、蚀日、幻晶原图为 RGB，采用统一的 Unity 圆角遮罩衔接，不宣称它们已输出透明通道；商品预览和实际玩家卡引用同一商品 SO 的 Sprite，并使用圆角遮罩。记录 Image 提示词与选择依据到 `Docs/NamecardArtNotes.md`。不覆盖现有用户资源。

## 9. 实际实现细节

- SO → `Poker/Shop/Export Server Catalog` →纯数据 JSON；Build 自动导出并校验。服务器启动固定加载目录，用 SHA-256 计算价格／上架版本，客户端确认使用服务器报价。
- `SqliteAccountRepository.Shop.cs` 的同一事务写余额、库存、负数账本与幂等结果。正常业务拒绝也保存处理结果；房间／活动手牌拒绝不产生消费记录。已处理请求先重放，不让旧装备重试覆盖后续装备。
- 私有库存只在本人 `NamecardShopResponse` 返回。公开 `RoomInfo.Namecards` 仅为玩家名 → 已装备 ID，随现有 JSON 房间同步和 ClientGameInfo.RoomInfo 投影发送；没有广播完整账户或库存。离线手牌参与者保留上一份公开外观，不在下注时访问库存数据库。
- 商店只由大厅入口显式调用 BeginOnline；Editor Preview 保持独立临时数据。关闭面板清理回调、确认窗口和请求状态；响应核对账户与请求号，超时最多重试三次并复用操作 ID。
- 下架使用商品 SO 的上架开关；已拥有者仍能看到和装备，默认款始终可用。新增默认账户无需批量补库存。
- 验证结果记录在 [商店验证记录](NamecardShopValidation.md)。
