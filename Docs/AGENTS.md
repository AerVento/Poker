# Docs 目录说明

`Docs/` 只描述项目**当前**的行为、配置和规范。它不是工作日志：过程记录写在任务交付说明里，不要留在这里。

## 放在哪里

| 目录 | 放什么 |
| --- | --- |
| `Systems/` | 某个系统现在如何运作：规则、配置方式、代码位置、容易出错的判定口径 |
| `Operations/` | 部署、配置文件、发布与运维操作 |
| `Standards/` | 必须遵守的规范（UI、美术标准等） |
| `Proposals/` | 已讨论但尚未实施的设计方案；实施后把结论写进 `Systems/` 并删除提案 |

以下内容不放进 `Docs/`：

- 测试报告、验证记录、截图、测试用例清单 → 写到 `Logs/`（不提交）或直接写在交付说明里。
- 实施计划、待确认问题、评审记录、带日期的更新日志 → 讨论结束后把结论合并进对应文档，原稿不保留。
- 美术提示词、生成原图、预览图、旧版素材 → `ArtSources/` 对应目录。
- 反复执行的操作流程 → 写成 `.agents/skills/` 下的 Skill，文档只描述规则本身。

## 写法

- 文件名用英文大驼峰，不带日期或版本号，如 `DailyTasks.md`。一个系统只保留一份文档，新增内容合并进去，不要再建“补充”“更新”“v2”之类的平行文件。
- 写“现在是什么样”，不写“这次改了什么”。规则变化时直接改写对应段落，不在文首追加“某日更新”。
- 写清玩家可见规则、配置入口和代码位置；需要时列出判定口径和边界。
- 文档描述系统与机制，不登记具体内容。物品、礼物、名片、牌面、任务、奖池奖品及其价格、权重、概率等以 `Configs/` 和代码为准，不在文档中逐项列出或复制数值；新增一件内容不应需要改系统文档，只有新增或改变机制时才更新。需要说明时引用配置字段或文件，例子只用来解释规则。
- 单款内容的设计记录（动画分镜、美术规范、角色清单、生成提示词）放在 `ArtSources/<类型>/<款式>/` 的 README 或设计文档中。第三方授权等影响整个产品的约束例外，可在系统文档中点名。不要复制大段代码，也不要记录作业编号、构建编号或日志路径。
- 引用代码和资源用仓库相对路径；链接用相对链接，移动文件后同步修改。
- 修改代码时，如果改变了文档描述的行为或配置，同一任务内更新对应文档；新增系统时在 `README.md` 的索引中加一行。
