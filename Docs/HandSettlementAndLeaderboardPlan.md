# 每手结算、排行榜与牌桌交互调整实施计划

更新：2026-09-06。

状态：本轮功能已实施并完成验证，包括后来追加的观战摊牌修复。本文保留决策及验收清单；实际结果与限制见 [验证记录](HandSettlementValidation.md)。名片商店另列下一阶段计划，已追加 UI／SO／美术原型，交易服务尚未实施。

## 1. 目标与已确认决策

1. 盲注、下注、跟注和 All-in 只改变服务端内存中的本手筹码、累计投入和奖池，不再因每次投注修改数据库。
2. 账户余额在每手结算时统一按净输赢更新。注册初始发放、每日奖励仍按现有规则独立入账；“每手结算”不限制这些合法的非牌局余额变动。
3. 排行榜显示全体账户中余额最高的前 10 名，包含离线账户。ScrollView 下方紧贴一行固定的本人排名、名称、余额，不随列表滚动。
4. 用户已明确选择：数据库发生致命故障时，沿用现有停服策略。重启后保留已提交的结算，作废未提交的牌局。不增加在线暂停重试、待结算队列或跨重启续玩。
5. 仍然是每手使用账户全部可用筹码，不引入买入、兑回或独立桌上钱包。区分账户余额和本手筹码，是区分结算值与运行时状态。
6. 正常断线、顶号、弃牌、预约离开不取消本手输赢。仍按既有规则自动操作和结算，All-in 权益保留。
7. 用户追加确认：移除服务器因长期没有业务活动而自动断开连接的机制。当前阈值为 300 秒；新规则下，连接正常的玩家可以持续停留在标题、排行榜、大厅、等待房间或旁观界面。牌局思考超时自动过牌/弃牌、连接建立超时、传输层真实失联检测及存储故障停服继续按原规则处理。
8. 用户追加要求：将局内设置面板中的预约离开、预约观战操作移到 `GamePanel` 左上角，玩家无需打开设置即可预约或取消。迁移包含对应的状态提示和状态变化后的操作；局内设置继续承载显示、音量等设置项。
9. 用户追加确认：“东山再起”领取条件由账户余额严格小于 1,000 改为小于等于 1,000。奖励仍为 2,000，每日一次、UTC+8 零点刷新、房间外领取及活动手牌限制继续沿用。
10. 用户已澄清：GamePanel 中所有金额 Label 在金额小于 1,000,000 时显示完整整数；从 1,000,000 起（含边界）按 K = 1,000 缩写。例如 500,000 显示 `$500000`，1,000,000 显示 `$1000K`。大额统一使用 K，不再自动切换 M/B；具体改动清单与格式样例见阶段 H。

11. 用户在验证期间追加修复：观战者应看见结算时已公开的摊牌底牌及牌型。`RoundResult.ForSpectator` 原先无差别清空所有底牌，改为复制 `CompleteRound` 已公开的牌；弃牌与未摊牌直接获胜仍不公开底牌，局中快照继续隐藏私有信息。同步修订原先错误地要求“观战结算全部无底牌”的测试和文档，增加实际网络与结果 UI 检查。

延续上一版计划的默认规则：入口放在大厅（房间列表页）；打开时查询，可手动刷新；按余额降序、注册时间升序、账户 ID 的稳定顺序排列，使用连续名次，不采用并列排名。自己进入前 10 时，榜内高亮且底部本人行仍保留。

故障策略与金额缩写规则均已确认，当前没有待答的必选问题。

## 2. 审查发现的冲突与遗漏

| 项目 | 当前证据与影响 | 修订方案 |
| --- | --- | --- |
| 结算失败重试与停服冲突 | `GuardedAccountRepository.Execute` 会锁死后续仓储访问；`NetworkRoom.HandleFatalStorageError` 调用 `GameManager.StopForStorageFailure` 清空内存牌局。原计划“保留状态并重试”无法直接成立。 | 按用户确认沿用全服停止；区分事务已提交和未提交，不承诺恢复未保存的胜负结果。 |
| 账户余额实际发送桌上筹码 | `CreateGameInfoSync` 对参赛者将 `player.Chips` 赋给 `AccountChips`；客户端再写入全局账户状态。只改数据库后，UI 仍会随下注扣余额。 | `AccountChips` 改为已结算余额；玩家列表、操作区继续使用本手剩余筹码；同步检查重连、旁观和大厅。 |
| 结算只处理收款账户 | `GameManager.ApplySettlement` 跳过收入为零者，仓储 `SettleHand` 也只遍历收入列表。旧模型中输家已在下注时扣款，因此成立；新模型中会漏扣输家。 | 改为覆盖开局参与者的完整结算清单，包含弃牌、断线、收入为零及净变化为零者。 |
| 旧数据库按已扣款投入退款 | 当前 schema 为 3，`RecoverAbandonedHands` 对所有 Active 手牌调用 `RefundAndAbortHand`。直接沿用新模式会有错误退款风险。 | 增加持久化记账模式标识与 schema 迁移；旧手按旧投入退款，新手只作废并释放占用。 |
| 账本与对账依赖逐笔扣款 | 当前对账使用 `HandCommit` 等旧流水与活动投入互相抵消。新模式手内不再存在扣款流水。 | 新结算使用有正有负的净变动流水；分别校验数据库账本和内存牌局守恒，不将奖池重复计入账户总额。 |
| 会话余额快照可能滞后 | `PlayerManager` 保存登录时的 `PlayerAccount` 副本；每日任务会更新副本，现有普通结算路径未统一更新它。 | 明确刷新结算后的在线会话快照；排行榜从仓储查询实际余额，会话只用于确定身份。 |
| 结算、离房和下一手相互依赖 | 当前结果展示和 10 秒倒计时后处理预约离开、旁观、释放座位与下一手资格。提前清理玩家会丢失未入账输赢。 | 先提交所有参与者结算，再更新显示与触发结果事件，按现有顺序处理座位及下一手；使用本手固定参与者清单。 |
| 旧故障测试依赖下注写库 | 现有 `DebitFailureRepository` 和 `FatalStorageTest.DebitStorageFailure...` 通过下注或盲注的数据库写入注入故障。取消写入后，这种预期不再适用。 | 将开局写入故障与结算故障独立测试；新增下注无写入的断言，保留全服停止和恢复的实际故障测试。 |
| 排名并非手内固定 | 自己的余额不变，但其他玩家的结算、奖励及新账户加入可能影响自己的名次。 | 修正验收口径：本人下注不改变本人已结算余额；每次打开/刷新按全体账户当时的余额重新排名。 |
| 空闲监控与牌局生命周期共用字段 | `ClientIdleTimeoutSeconds = 300`，每秒检查业务活动；但 `_serverActivityMonitorVersion` 同时保护阶段推进、结算倒计时和旁观者返回大厅等异步任务。直接整体删除会破坏停服/重启保护。 | 删除业务空闲记录、监控和踢人消息；保留服务器生命周期版本及所有非空闲任务的校验，必要时将字段改成准确表达服务器生命周期的名称。 |
| 预约按钮目前随设置面板开关绑定 | `InGameOptionPanel.Bind` 将按钮临时交给 `GamePanel.AttachSettingsControls`；关闭设置调用 `DetachSettingsControls`，移除监听并清空引用。只移动 prefab 节点会导致牌桌按钮失效。 | 改由 GamePanel 序列化持有并管理按钮生命周期，移除设置页的临时绑定；同时更新依赖“先打开设置再点预约”的 UI 测试与集成驱动。 |
| 东山再起的条件在多层重复判断 | `DailyTaskService.GetStatus` 当前以 `>= 1000` 判定超标；领取路径向 `ClaimDailyReward` 传排他上限，SQLite 事务也用 `>=` 拒绝。UI 提示还是“不低于 $1,000”。 | 统一为仅 `> 1000` 拒绝；仓储参数命名、任务描述、UI 错误提示和边界测试同步调整。 |
| 金额格式散落且混用 | GamePanel 目录下 6 个类各自有 `BigNumberToString`，从 1,000 起使用 K/M/B；账户、资格和输入纠正提示使用 `N0`。只改玩家行会留下多种金额口径。 | 提取一个纯 C# 金额格式化入口，覆盖阶段 H 的具体清单；输入框仍保留可编辑的完整整数，实际筹码和网络金额不变。 |

主要依据：[GameManager](../Assets/Scripts/Network/GameManager.cs)、[SQLite 仓储](../Assets/Scripts/Network/Accounts/SqliteAccountRepository.cs)、[仓储保护层](../Assets/Scripts/Network/Accounts/GuardedAccountRepository.cs)、[NetworkRoom](../Assets/Scripts/Network/NetworkRoom.cs)、[PlayerManager](../Assets/Scripts/Network/PlayerManager.cs)。

当前行为文档：[存储异常停服](FatalStorageShutdown.md)、[旁观生命周期](SpectatorLifecycle.md)、[房间生命周期](RoomLifecycle.md)、[每日任务](DailyTasks.md)、[UI 导航](UINavigationReview.md)。早期 [账户筹码改造计划](CashGameMigrationPlan.md) 中的逐笔入账和活动奖池对账口径将在实施后标明被本方案替代；它不是本次继续逐笔扣款的约束。

## 3. 账户余额与本手状态

### 3.1 数据含义

| 数据 | 含义与更新时点 | 使用场景 |
| --- | --- | --- |
| `PlayerAccount.Chips` | 最近一次成功入账后的账户余额；牌局内只在本手结算时改变。 | 排行榜、账户余额显示、开局资格。 |
| `HandStartingChips` | 本手开局时从服务器账户数据取得的固定筹码上限。 | 投入上限、结算校验、当前手内的余额展示依据。 |
| `ServerGameInfo.PlayerInfo.Chips` | 当前手剩余筹码；下注在内存中扣减。 | 牌桌玩家筹码、下注上限、跟注与 All-in。 |
| `StageBet` / `RoundBet` / `TotalPot` | 当前街投入、本手累计投入及奖池，均为服务端内存状态。 | 轮次推进、加注校验、奖池与边池计算。 |

一手结束后，本手筹码和已结算账户余额对齐。等待下一手或旁观时，显示最新账户余额；不能把上一手的 `HandStartingChips` 当作当前余额。

### 3.2 必须成立的约束

- 一手开始时冻结参与者身份与初始筹码，累计投入不超过初始筹码；不得从客户端取得结算金额或参与者清单。
- 同一账户只能参与一个活动手牌。数据库保留活动手牌与参与者记录，现有房间归属、会话验证和账户占用检查继续生效。
- 每日任务仍要求离开房间；数据库层仍拒绝活动手牌期间的其他余额变更。不得因为数据库余额未降低而允许再领取或重复使用筹码。
- 元数据更新与余额变更分开考虑。登录、会话轮换、LastRoomId 等变化不能因为共享 `Version` 就被误判为本手筹码遭篡改。
- 所有净输赢运算先使用足够宽的有符号整数并检查范围，不能直接用 `uint` 相减。账户及奖池继续遵守现有整数上限，不扩大筹码上限。

结算时对每位参与者：

```text
净变化 = 获得的奖池分配 + 未被跟注的退款 - 本手累计投入
结算后余额 = 开局账户余额 + 净变化
```

同一手的全部净变化之和必须为 0。退款只计算一次，主池、边池是累计投入的分配方式，不能再与累计投入重复相加。现有结果界面 `ChipEarned` 的奖金展示含义继续沿用，不直接替换为净输赢。

## 4. 分阶段实施

### 阶段 0：移除业务空闲自动踢人

1. 删除 `ClientIdleTimeoutSeconds`、`ClientIdleMonitorIntervalMilliseconds`、`_lastClientActivities`、`_idleDisconnectPending`、`MonitorClientActivity` 和 `DisconnectIdleClient`，移除启动监控及停止/断线时专用清理代码。不会以增大超时时间或发送假活动的方式规避踢人。
2. 删除 `RecordClientActivity` 及 `NetworkRoom`、`AccountAuthenticator`、`NetworkRoom.DailyTasks` 中仅服务于业务空闲判定的调用。认证、会话轮换、房间处理与请求限频继续正常执行；排行榜也不再接入这套活动记录。
3. 删除 `AccountAuthenticationMessages.cs` 中的 `ServerIdleDisconnectNotice`，同步删除客户端注册和接收处理器。该文件还包含其他认证/停服消息，保留文件和原 `.meta`；不因清理单个类型而删除整个文件。
4. 保留 `_serverActivityMonitorVersion` 承担的服务器生命周期作用：服务启动、停止和致命故障时更新；阶段推进、结果倒计时、旁观返回等等待之后仍必须校验版本与当前牌局引用。必要时统一改名为 `_serverLifecycleVersion`，并检查全部引用。
5. `ServerIdleDisconnectNoticeHandler` 目前只设置 `_silentDisconnect`；删除该处理器后保留 `_silentDisconnect` 本身及其在静默连接、连接失败、登出等其他路径的用途，避免误改断线提示。
6. 保留牌局思考计时和自动操作、10 秒下一手倒计时、客户端连接建立超时、Mirror/传输层心跳与真正失联检测、认证失败/顶号断开、用户登出和致命存储故障停服。这些机制不属于本次取消的业务空闲踢人。
7. 移除空闲踢人不会使玩家因不操作而免于牌局超时规则，也不会释放其房间归属或取消手牌。服务器继续按照既有规则推进和结算。

### 阶段 A：迁移、仓储与结算契约

1. 将当前 schema 3 按正式迁移流程升级（预期为 4），添加手牌记账模式标识，例如“逐笔扣款”与“结束结算”。已有手牌标记为旧模式，新建手牌显式使用新模式；不能仅根据当前程序版本判断历史手牌含义。
2. 迁移与版本更新在事务中完成，可重复初始化；新库与旧库得到一致结构。迁移成功后、接受登录和牌局请求前完成活动手牌恢复。
3. 保留旧版已扣款 Active 手牌的幂等退款路径；新模式 Active 手牌作废时不修改余额、不生成退款。Settled 手牌不得重新作废或重复入账。
4. 以完整参与者结算条目替换只含收款人的接口。条目包含账户 ID、累计投入、奖金与退款，仓储结合开局快照验证参与者无重复、无遗漏、无额外账户、投入不超限及总额守恒。
5. 一个结算事务中更新所有账户余额、写入净变动流水、保存最终参与者结算摘要、标记 Settled 并释放活动占用。零净变化者仍保留结算摘要，可不写无意义的余额 UPDATE。
6. 结算唯一标识绑定 HandId。重复提交同一结果不再入账；同 HandId 的冲突结果不得静默当成成功。返回已保存的结算结果，不能拿账户后来发生奖励或下一手后的余额冒充历史结果。
7. 同步修改 `IHandAccountRepository`、`GuardedAccountRepository` 及测试仓储。移除运行时投注对 `ApplyHandDebits` 的依赖；保留历史数据解读能力，不因清理接口而删掉旧账本。
8. 更新对账：数据库账户余额与账本净额一致；新模式每手净变化为 0；旧模式退款记录仍可核对。活动新牌局的实时投入只在内存校验，不能宣称数据库能逐笔复盘未完成牌局。

部署条件：停止旧服务器并备份数据库后升级；同一数据库由一个正式服务器实例管理。旧程序不得重新打开升级后的数据库；现有“拒绝更高 schema”保护继续生效。迁移测试只操作隔离副本，不直接修改用户实际账户数据。

### 阶段 B：盲注、下注与完成事件

1. 改造 `CommitChips`、`PostBlinds`、`ApplyCommittedBlind`：完成全部输入及范围校验后，一次性更新内存中的筹码、投入、奖池和 All-in 状态。盲注两名玩家的更新也不得留下半完成状态。
2. 保留服务端行动玩家、HandId、TurnId、最小加注、短筹码跟注、加注重新开放等校验。ActionSequence 仍推进，但不再用每步数据库请求记录实现动作保护。
3. 重复或上一手的下注请求不得再次扣内存筹码。检查 Check、Fold、Bet、Call、All-in、自动操作和超时操作的事件次数与推进顺序。
4. 常规摊牌、所有人弃牌后的提前结束、All-in 自动发完公共牌使用同一结算入口。数据库成功后才进入 RoundOver、清奖池、发送结果和启动下一手倒计时。
5. 结算异常或结果被仓储拒绝时触发现有全服停止流程，不继续完成事件、不释放玩家去新房间、不在停服中退款或重试。
6. 取消手牌、开局失败和房间清理按记账模式作废；成功结算后的清理不得撤销结果。删除下注写入后，存储故障可能在下一次数据库操作才被发现，不能再承诺每次下注都探测数据库健康。

手内“无投注写库”的范围是：不因下注更新账户表、参与者投入、账本或手牌请求表。认证、房间关联、账户查询等已有职责仍可访问数据库，不把需求扩大为运行期间禁止所有数据库访问。

### 阶段 C：余额同步、重连与房间生命周期

1. `CreateGameInfoSync` 的 `AccountChips` 使用正确的已结算余额；牌桌列表和操作区继续消费本手 `Chips`。尽量复用开局快照和结算后缓存，不为每名参赛者的每次广播新增数据库查询。
2. 成功结算后刷新当前在线会话的账户快照，并同步客户端全局状态、大厅、牌桌账户栏。离线账户同样入账，重新登录读取数据库；顶号后只能更新当前有效会话。
3. 同步检查 `GameInfoSync`、`AccountBalanceSync`、`ClientGameInfo`、`Serialization.cs` 和 UI 消费端。新增内部状态只在确有需要时同步，不泄漏其他玩家底牌、密码资料或仅服务端可见字段。
4. 本手参与者在结果入账前不能从结算清单中消失，包括已弃牌、All-in、断线、预约离房和预约旁观者。中途加入的旁观者不进入本手结算清单。

### 阶段 H：GamePanel 全部金额 Label 统一格式

**已确认规则：** 金额 `< 1,000,000` 显示完整整数；金额 `>= 1,000,000` 除以 1,000 并加 `K`。不自动转换为 M 或 B。普通金额保留 `$`，结算奖金保留 `+$`，数字不加千分位分隔符，与用户给出的完整金额示例一致。

实现细节：缩写值默认沿用现有最多一位小数的精度，省略末尾 `.0`；舍入使用现有的 `MidpointRounding.ToEven` 规则，通过 decimal 或整数运算实现，避免 float 丢失精度。小于阈值的金额不舍入。所有入口采用同一种小数点格式，不随机器区域设置变化。
